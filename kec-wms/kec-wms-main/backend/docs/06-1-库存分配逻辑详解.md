# 库存分配逻辑详细说明

## 背景与目标

库存分配是出库订单处理的核心环节，负责将订单需求与实际库存进行匹配和预留。本文档详细说明WMS系统中库存分配的完整流程、并发控制机制和关键实现细节。

## 核心概念

### 1. 库存桶（InventoryBucket）系统

库存桶是库存管理的基础单元，按以下维度聚合：
- **维度组合**：租户 + 仓库 + 库区 + 库位 + SKU + 批次号 + LPN + 桶类型
- **桶类型**：
  - `AVAILABLE`：可用库存（可以被分配）
  - `ALLOCATED`：已分配库存（已预留给订单）
  - `PICKED`：已拣货库存
  - `PACKED`：已打包库存
  - `SHIPPED`：已发货库存

### 2. 分配策略（AllocationStrategy）

系统支持三种库存分配策略：
- **FIFO**（先进先出）：按 `fifoDate` 升序，优先分配最早入库的库存
- **FEFO**（先到期先出）：按 `expiryDate` 升序，优先分配最早到期的库存
- **LIFO**（后进先出）：按 `fifoDate` 降序，优先分配最晚入库的库存

策略配置优先级：`ClientWarehouse.config` > `Client.config` > 默认值（FIFO）

### 3. 分配模式（AllocationMode）

- **FAST 模式**：直接获取分布式锁，快速分配，适合低并发场景
- **FAIR 模式**：使用公平队列，保证先到先得，适合高并发场景

## 库存分配完整流程

### 阶段1：订单创建与入队

**文件位置**：`backend/src/app/api/v1/outbound-orders/route.ts`

1. **创建出库订单**（POST `/api/v1/outbound-orders`）
   - 验证客户、仓库、SKU信息
   - 使用分布式锁保护订单号生成（避免重复）
   - 创建订单主表、订单行、地址、时间线记录
   - 订单初始状态：`PENDING`

2. **自动加入分配队列**
   ```typescript
   await queueInventoryAllocation(
     { id, orderNumber, warehouseId, clientId },
     tenantId,
     userId
   )
   ```
   - 调用 `queueInventoryAllocation()` 创建后台任务
   - 任务类型：`INVENTORY_ALLOCATION`
   - 使用BullMQ队列异步处理

### 阶段2：分配任务执行

**文件位置**：`backend/src/lib/queue/workers/inventory-allocation.worker.ts`

#### 2.1 Worker处理流程

```
InventoryAllocationWorker.process()
  ↓
  遍历每个订单ID
  ↓
  allocateOrderInventory() - 分配单个订单
  ↓
  根据模式选择：
  - FAIR模式 → allocateWithFairQueue()
  - FAST模式 → allocateWithLock()
  ↓
  doAllocate() - 执行实际分配
```

#### 2.2 并发控制机制

**FAST模式**（默认）：
1. 收集订单所需的所有SKU ID，并按字母顺序排序（避免死锁）
2. 按顺序获取每个SKU的分布式锁
   - 锁键格式：`inventory-allocation-lock:{warehouseId}:{skuId}`
   - 锁TTL：60秒
   - 最大重试：50次，间隔100ms
3. 如果任一锁获取失败，释放所有已获取的锁，返回失败
4. 获取所有锁后，执行分配逻辑
5. 完成后释放所有锁

**FAIR模式**：
1. 为每个SKU加入公平队列（Redis List）
2. 等待所有SKU都排在队列第一位（最多等待30秒）
3. 轮到自己后，调用FAST模式的锁机制执行分配
4. 完成后离开所有队列

#### 2.3 核心分配逻辑（doAllocate）

**步骤1：查找可用库存**
```typescript
const buckets = await prisma.inventoryBucket.findMany({
  where: {
    tenantId,
    warehouseId,
    skuId: line.skuId,
    bucketType: 'AVAILABLE',  // 只查可用库存
    quantity: { gt: 0 },
  },
  orderBy: orderByField,  // 根据策略排序
})
```

**步骤2：按订单行分配库存**
- 遍历每个订单行
- 计算需求数量：`requiredQty = orderedQty - allocatedQty`
- 从可用库存桶中按策略顺序提取库存
- 如果库存不足，标记订单为 `OUT_OF_STOCK`，分配失败

**步骤3：事务中执行状态转换**
```typescript
await prisma.$transaction(async (tx) => {
  // 对每条分配记录：
  for (const record of allocationRecords) {
    // 3.1 乐观锁检查
    const currentBucket = await tx.inventoryBucket.findUnique({
      where: { id: record.bucketId },
      select: { quantity: true, version: true },
    })
    if (currentBucket.quantity < record.qty) {
      throw new Error('库存已被其他任务分配')
    }

    // 3.2 扣减AVAILABLE桶数量
    await tx.inventoryBucket.update({
      where: { id: record.bucketId },
      data: {
        quantity: { decrement: record.qty },
        version: { increment: 1 },  // 版本号+1
      },
    })

    // 3.3 增加ALLOCATED桶数量（或创建新桶）
    await tx.inventoryBucket.upsert({
      where: { /* 唯一键 */ },
      update: { quantity: { increment: record.qty } },
      create: { /* 新建ALLOCATED桶 */ },
    })

    // 3.4 创建分配明细记录
    await tx.allocationDetail.create({
      data: {
        bucketId: record.bucketId,
        skuId: record.skuId,
        locationId: record.locationId,
        allocatedQty: record.qty,
        referenceType: 'OUTBOUND_ORDER',
        referenceId: order.id,
        referenceLineId: record.lineId,
        status: 'ALLOCATED',
      },
    })

    // 3.5 更新库存快照（InventorySnapshot）
    await tx.inventorySnapshot.updateMany({
      where: { tenantId, warehouseId, locationId, skuId },
      data: {
        qtyAvailable: { decrement: record.qty },
        qtyAllocated: { increment: record.qty },
      },
    })
  }

  // 3.6 更新订单行状态
  await tx.outboundOrderLine.update({
    where: { id: lineId },
    data: {
      allocatedQty: { increment: allocatedQty },
      status: 'ALLOCATED',
    },
  })

  // 3.7 更新订单汇总和状态
  await tx.outboundOrder.update({
    where: { id: order.id },
    data: {
      totalAllocatedQty: { increment: totalAllocated },
      status: 'ALLOCATED',
    },
  })

  // 3.8 更新订单时间线
  await tx.orderTimeline.upsert({
    where: { orderId: order.id },
    update: { allocatedAt: new Date(), allocatedBy: userId },
    create: { /* ... */ },
  })
})
```

### 阶段3：同步分配（可选）

**文件位置**：`backend/src/lib/services/inventory-allocation-service.ts`

除了异步队列分配，系统还提供同步分配接口：

```typescript
allocateInventorySync(orderId, tenantId, userId)
```

**特点**：
- 使用分配锁（`withAllocationLock`）防止同一订单并发分配
- 预检查库存是否充足（`checkInventoryAvailability`）
- 使用事件溯源模式记录库存变化
- 支持批量分配（`/api/v1/outbound-orders/batch-allocate`）

**与Worker的区别**：
- Worker版本：使用旧的直接更新桶的方式
- Service版本：使用事件溯源，通过 `createAllocateEvents()` 创建事件记录

## 数据库表结构

### 核心表

1. **InventoryBucket**（库存桶）
   - 唯一约束：`[locationId, skuId, batchNumber, lpn, expiryDate, bucketType, asnNumber]`
   - 关键字段：`quantity`（数量）、`version`（乐观锁版本号）、`bucketType`（桶类型）

2. **AllocationDetail**（分配明细）
   - 记录每次分配的详细信息
   - 关键字段：`allocatedQty`、`pickedQty`、`shippedQty`
   - 关联：`referenceType`、`referenceId`（订单ID）、`referenceLineId`（订单行ID）

3. **InventorySnapshot**（库存快照）
   - 按库位+SKU维度的库存汇总
   - 关键字段：`qtyAvailable`、`qtyAllocated`、`qtyPicked`等

4. **OutboundOrder**（出库订单）
   - 状态流转：`PENDING` → `ALLOCATED` → `PICKING` → `PICKED` → `PACKED` → `SHIPPED`
   - 汇总字段：`totalOrderedQty`、`totalAllocatedQty`、`totalPickedQty`等

## 并发安全机制

### 1. 分布式锁（Redis）

**锁粒度层级**：
- **Bucket级**：最细粒度，锁定单个库存桶
- **SKU级**：锁定仓库内某个SKU的所有库存
- **Order级**：锁定订单级别的操作
- **Allocation级**：专门用于分配操作的锁

**锁配置**：
```typescript
DEFAULT_LOCK_OPTIONS = {
  ttlMs: 30000,      // 30秒超时
  retryCount: 5,     // 重试5次
  retryDelayMs: 100, // 重试间隔100ms
}
```

### 2. 乐观锁（数据库）

在事务中更新库存桶时，使用 `version` 字段进行乐观锁检查：
```typescript
const currentBucket = await tx.inventoryBucket.findUnique({
  where: { id: bucketId },
  select: { quantity: true, version: true },
})

if (currentBucket.quantity < allocateQty) {
  throw new Error('库存已被其他任务分配')
}

await tx.inventoryBucket.update({
  where: { id: bucketId },
  data: {
    quantity: { decrement: allocateQty },
    version: { increment: 1 },  // 版本号递增
  },
})
```

### 3. 死锁避免

- 对需要锁定的SKU ID进行排序（字母顺序）
- 所有线程按相同顺序获取锁
- 如果获取失败，释放所有已获取的锁后重试

## 库存释放（取消分配）

**文件位置**：`backend/src/lib/services/inventory-allocation-service.ts`

```typescript
deallocateInventorySync(orderId, tenantId, userId)
```

**流程**：
1. 检查订单状态必须为 `ALLOCATED`
2. 查找所有 `ALLOCATED` 类型的库存桶
3. 创建取消分配事件（`createDeallocateEvents`）
4. 反向操作：
   - `ALLOCATED` 桶数量减少
   - `AVAILABLE` 桶数量增加
5. 更新订单状态为 `PENDING`
6. 记录操作日志

### 库存状态转换流程

```
入库上架
   ↓
AVAILABLE（可用库存）
   ↓ 订单分配
ALLOCATED（已分配库存）
   ↓ 拣货

   ↓ 打包

   ↓ 发货

```

### 并发控制示意

```
订单A需要SKU1、SKU2
订单B需要SKU2、SKU3

按字母顺序排序后：
订单A：[SKU1, SKU2]
订单B：[SKU2, SKU3]

两个订单都按相同顺序获取锁，避免死锁
```

## 总结

库存分配系统采用了多层次的并发控制机制，确保在高并发场景下的数据一致性：

1. **分布式锁**：防止多个任务同时操作同一SKU
2. **乐观锁**：在数据库层面检测并发冲突
3. **事务保证**：所有状态变更在单个事务中完成
4. **事件溯源**：记录所有库存变化历史，可追溯和审计

系统支持灵活的分配策略配置，可根据业务需求选择FIFO、FEFO或LIFO策略，同时提供FAST和FAIR两种模式适应不同的并发场景。
