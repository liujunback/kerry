# 差异确认调整与结算

## 1. 覆盖入口

后端入口：

- `POST /api/v1/inventory/counts/[id]/recounts/generate`
- `POST /api/v1/inventory/counts/[id]/differences/confirm`
- `POST /api/v1/inventory/counts/[id]/settle`
- `POST /api/v1/inventory/counts/[id]/disposals/[disposalId]/start`
- `POST /api/v1/inventory/counts/[id]/disposals/[disposalId]/complete`

服务入口：

- `recount.ts`
- `recount-batch.ts`
- `adjustment.ts`
- `disposal.ts`
- `settlement.ts`

## 2. 复盘生成

复盘可以由完成初盘批次时自动生成，也可以通过接口手动生成。复盘批次来源是 `RECOUNT_PENDING`（待复盘）明细。

复盘批次创建后：

- 新增 `InventoryCountBatch`（盘点批次），类型为 `RECOUNT`
- 新增对应 `InventoryCountRoundLine`（盘点轮次行），类型为 `RECOUNT`
- 原初盘批次进入 `PENDING_RECOUNT` 或后续完成状态

## 3. 差异确认

`confirmInventoryCountDifferences`（确认盘点差异）会处理复盘后的差异：

- 如果仍有未完成复盘批次，会阻止确认。
- 对 `RECOUNTED`（已复盘）且非零差异的明细执行调整准备。
- 无差异或已确认的明细会进入 `CONFIRMED`。
- 需要后续处理的差异会生成差异处理单。

## 4. 库存调整

盘点差异复用 `inventory_adjustment`（库存调整）：

- 盘亏会从 `COUNT_HOLD`（盘点锁定桶）转出到 `COUNT_SHORTAGE`（盘亏桶）
- 盘盈会写入 `COUNT_SURPLUS`（盘盈桶）
- 会创建库存调整事件
- 会更新库存桶
- 会释放关联盘点锁
- 明细状态从 `CONFIRMED` 或 `ADJUST_CREATED` 推进到 `ADJUSTED`

执行调整时会按库存来源 FIFO（先进先出）排序，并保留 ASN（入库通知单）号、批次、效期、LPN（容器号）等库存维度。

## 5. 差异处理单

盘点差异处理单 `inventory_count_disposal` 用于处理调整后仍需要人工动作的差异。当前状态：

- `PENDING`
- `PROCESSING`
- `DONE`
- `CANCELLED`

开始处理会从 `PENDING` 到 `PROCESSING`。完成处理会写目标库位、备注、处理时间，并把状态更新为 `DONE`。

## 6. 结算

`settleInventoryCountOrder`（结算盘点单）会做强检查：

1. 如果有非零差异但未生成调整单，会先生成差异处理。
2. 如果有调整单但未生成差异处理单，会确保差异处理单存在。
3. 如果存在 `PENDING` 或 `PROCESSING` 的差异处理单，阻止结算。
4. 如果仍有未确认、未生成调整单或未调整的明细，阻止结算。
5. 对需要执行的调整再次执行或确认。
6. 批次统一更新为 `COMPLETED`。
7. 盘点单进入最终完成状态。

## 7. 排查建议

排查盘点差异时按这个顺序看：

1. `inventory_count_round_line` 是否有正确提交数量。
2. `inventory_count_detail` 的 `finalQuantity` 和 `diffQuantity` 是否正确。
3. `inventory_adjustment` 是否已生成和执行。
4. `inventory_count_disposal` 是否还有未完成记录。
5. `inventory_count_lock` 是否已释放。
6. `inventory_bucket` 中 `COUNT_HOLD`、`COUNT_SURPLUS`、`COUNT_SHORTAGE` 是否符合预期。
