# 库存锁与并发控制

## 1. 覆盖范围

本文件专门解释当前代码里库存相关的锁。

重点来源：

- `backend/src/lib/db/distributed-lock.ts`
- `backend/src/lib/services/inventory-lock-service.ts`
- `backend/src/lib/services/inventory-bucket-service.ts`
- `backend/src/lib/services/inventory-operation-service.ts`
- 各业务路由里的 `FOR UPDATE`

## 2. 当前锁模型分两层

## 2.1 第一层：Redis 分布式锁

当前项目通过 `distributed-lock.ts` 提供 Redis 锁，底层是：

- `SET NX EX`

关键特点：

- 有 TTL
- 有重试次数
- 释放锁时用 Lua 脚本校验 lockId
- 只有持锁者本人能释放

这层锁解决的是：

- 跨请求并发
- 跨进程并发
- 同一资源的重复进入

## 2.2 第二层：数据库事务锁

进入具体业务事务后，很多地方还会继续用：

- `SELECT ... FOR UPDATE`

这层锁解决的是：

- 同一行业务记录在同一个数据库事务内不被并发修改
- 防止单据重复执行
- 防止基于旧状态重复推进业务

所以当前库存并发控制不是“只靠 Redis”，也不是“只靠数据库”，而是两层一起用。

## 3. `inventory-lock-service.ts` 定义了哪些锁

当前统一封装了以下资源类型：

- `BUCKET`
- `LOCATION`
- `SKU`
- `ORDER`
- `ALLOCATION`

## 3.1 bucket 锁

粒度最细。

锁 key 维度包括：

- `tenantId`
- `warehouseId`
- `locationId`
- `skuId`
- `batchNumber`
- `lpn`
- `asnNumber`
- `expiryDate`
- `bucketType`

也就是说，当前 bucket 锁是按照“真实库存桶维度”来锁的。

这很重要，因为它能避免：

- 同一个 bucket 被并发加减
- 不同 bucket 之间被误伤

## 3.2 location 锁

粒度：

- `tenantId + locationId`

适合：

- 上架
- 涉及货位操作的场景

## 3.3 sku 锁

粒度：

- `tenantId + warehouseId + skuId`

适合：

- 上架
- 需要在一个仓里对同一 SKU 做串行化处理的场景

## 3.4 order 锁

粒度：

- `tenantId + orderId`

更偏业务单据保护。

## 3.5 allocation 锁

粒度：

- `tenantId + orderId`

专门用于库存分配/取消分配。

## 4. 锁是怎么排序避免死锁的

`inventory-lock-service.ts` 在处理多资源锁时，会：

1. 先把资源解析成统一的 `prefix:key`
2. 去重
3. 再按字典序排序
4. 按固定顺序依次加锁
5. 释放时倒序释放

这意味着当前代码不是“想到哪个锁哪个”，而是主动做了稳定顺序控制。

这对下面这些多 bucket 操作尤其重要：

- 分配
- 解冻
- 调整
- 移库
- 发货扣减

## 5. bucket 更新为什么还要再排序

在 `inventory-bucket-service.ts` 的 `updateBucketsInTransaction()` 里，更新前会再次按 bucket 维度排序，然后统一通过：

- `withInventoryLocks()`

拿 bucket 锁。

目的有两个：

1. 多 bucket 操作的加锁顺序稳定
2. 降低交叉加锁导致的死锁风险

## 6. 各类库存动作实际怎么锁

## 6.1 上架

SKU 上架和容器上架都使用：

- `withSkuLock(tenantId, warehouseId, skuId)`

然后在事务内对：

- `putaway_order_line`
- `putaway_order`
- `asn`
- `asn_line`

使用 `FOR UPDATE` 锁业务行。

随后库存层更新时，`updateBucketsInTransaction()` 再拿 bucket 锁。

所以它是三层保护：

1. SKU 锁
2. 业务单据行锁
3. bucket 锁

## 6.2 冻结 / 解冻

`freeze()` 和 `unfreeze()` 本身不显式包 `withLocationLock/withSkuLock`，但在库存更新时会进入：

- `updateBucketsInTransaction()`

也就是最终由 bucket 锁保护库存桶更新。

同时，`freeze()` / `unfreeze()` 会先读取源 bucket，并检查数量是否足够。

## 6.3 调整

`adjust()` 的核心保护也是：

- 先检查源 bucket 数量是否足够
- 再调用 `updateBucketsInTransaction()`

因此数量变化最终靠 bucket 锁串行化。

调整单执行接口另外还会对：

- `inventory_adjustment`

执行 `FOR UPDATE`，避免同一张调整单被重复执行。

## 6.4 移库

`transfer()` 更新源 bucket 和目标 bucket。

如果走 `transferWithLock()`，会先按固定顺序拿两个 location 锁，避免源/目标交叉死锁。

在当前移库单执行接口中，虽然直接调用的是 `transfer()`，但 `updateBucketsInTransaction()` 依然会对源 bucket、目标 bucket 做排序加锁。

另外，移库单执行前还会对：

- `inventory_transfer`

做 `FOR UPDATE`，防止重复执行。

## 6.5 分配

库存分配 `allocateInventorySync()` 会先用：

- `withAllocationLock(tenantId, orderId)`

把同一订单的分配动作串行化。

进入事务后，还会重新检查：

- 订单状态
- 可用 bucket

并在实际改库存时，通过：

- `createAllocateEvents()`
- `updateBucketsInTransaction()`

把 `AVAILABLE -> ALLOCATED`

这里的保护链是：

1. allocation 锁
2. 订单事务
3. bucket 锁

## 6.6 取消分配

`deallocateInventorySync()` 也使用：

- `withAllocationLock(tenantId, orderId)`

再在事务里把：

- `ALLOCATED -> AVAILABLE`

并回写订单与订单行状态。

## 6.7 发货扣减

签出时真正扣减库存发生在：

- `checkout-service.ts -> shipOrderInTransaction() -> ship()`

这里会先对每条分配记录对应的 bucket 执行：

- `withBucketLock(...)`

然后再调用 `ship()`。

`ship()` 内部最终仍然会走 bucket 更新。

这表示发货扣减是以具体 bucket 为粒度串行的。

## 7. `FOR UPDATE` 主要锁了哪些业务表

当前代码中，以下表在关键节点会被 `FOR UPDATE`：

- `asn`
- `asn_line`
- `putaway_order`
- `putaway_order_line`
- `receiving_record`
- `container_item`
- `inventory_adjustment`
- `inventory_transfer`

它们的作用不是保护 bucket，而是保护业务单据状态推进本身。

## 8. 当前锁矩阵

| 动作 | 分布式锁 | 数据库锁 | 目的 |
| --- | --- | --- | --- |
| 上架 | `withSkuLock` | `putaway_order_line/asn/... FOR UPDATE` | 防止同 SKU 并发上架、重复推进单据 |
| bucket 更新 | `withInventoryLocks` | 无额外业务行锁 | 防止同 bucket 并发改数量 |
| 分配 | `withAllocationLock` | 订单事务内重查 | 防止同订单重复分配 |
| 取消分配 | `withAllocationLock` | 订单事务内重查 | 防止同订单重复取消 |
| 发货 | `withBucketLock` | checkout 事务 | 防止同分配 bucket 被并发扣减 |
| 调整执行 | bucket 锁 | `inventory_adjustment FOR UPDATE` | 防止调整单重复执行、超调 |
| 移库执行 | bucket 锁 | `inventory_transfer FOR UPDATE` | 防止移库单重复执行 |

## 9. 当前代码里的并发现实与边界

## 9.1 锁不是无限期的

Redis 锁有 TTL：

- 默认 30 秒
- 长锁 60 秒

这意味着极长事务如果超过 TTL，理论上会带来锁续期之外的并发复杂性。

当前代码没有做自动续租。

## 9.2 snapshot / summary 不在主事务锁里

主事务只保证：

- 事件
- bucket
- 单据回写

而：

- `inventory_snapshot`
- `sku_inventory_summary`

是在事务后刷新，不受主事务强一致保护。

所以短时间窗口里可能出现：

- bucket 已变
- snapshot 还没刷新

## 9.3 `pick()` 服务已实现，但当前主业务入口没有明显直接调用

当前仓库里：

- `inventory-operation-service.ts` 有 `pick()`
- 但主路由搜索下，库存变化主链里更清晰被调用的是：
  - 分配
  - 取消分配
  - 发货扣减

因此文档里要把 `pick()` 标成：

- “已有库存操作实现”
- “当前主入口未明显直接接线”

而不能写成当前主链必经节点。

## 10. 本文件小结

当前库存锁的核心思路是：

1. 先用 Redis 分布式锁把同一资源串行化
2. 再在数据库事务里用 `FOR UPDATE` 锁关键业务行
3. 真正改库存时再按 bucket 维度稳定排序并加锁

这套设计的目标不是绝对消灭所有并发复杂性，而是把最容易出问题的地方压住：

- 同单重复执行
- 同 bucket 超扣
- 多 bucket 更新死锁
