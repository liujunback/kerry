# 库存总览与数据分层

## 1. 覆盖范围

本文件解释库存系统的基础结构，不只看接口，还看底层表和汇总关系。

重点对应：

- `backend/prisma/schema.prisma`
- `backend/src/app/api/v1/inventory/route.ts`
- `backend/src/app/api/v1/inventory/summary/route.ts`
- `backend/src/app/api/v1/inventory/transactions/route.ts`
- `backend/src/lib/services/inventory-event-service.ts`
- `backend/src/lib/services/inventory-bucket-service.ts`
- `backend/src/lib/services/inventory-snapshot-service.ts`

## 2. 当前库存系统的四层结构

## 2.1 事件层：`inventory_event`

这是库存流水层，记录“发生过什么变化”。

核心字段：

- `event_type`
- `bucket_type`
- `quantity_delta`
- `quantity_before`
- `quantity_after`
- `reference_type`
- `reference_id`
- `reference_number`
- `reference_line_id`
- `location_id`
- `sku_id`
- `batch_number`
- `lpn`
- `event_date`
- `operator_id`

它回答的是：

- 这次是上架、分配、解冻、移库还是发货
- 改的是哪类 bucket
- 改之前多少
- 改之后多少
- 是谁触发的
- 关联的是哪张业务单据

它不直接回答页面“现在还有多少库存”，因为它只是流水。

## 2.2 事实层：`inventory_bucket`

这是当前代码里的库存事实层，也是最关键的一层。

当前唯一维度是：

- `location_id`
- `sku_id`
- `batch_number`
- `lpn`
- `expiry_date`
- `bucket_type`
- `asn_number`

也就是说，库存不是简单按“货位 + SKU”来存，而是细到：

- 批次
- LPN
- 效期
- bucket 类型
- ASN 来源号

核心字段：

- `bucket_type`
- `quantity`
- `asn_number`
- `fifo_date`
- `expiry_date`
- `production_date`
- `version`

当前 bucket 类型包括：

- `AVAILABLE`
- `ALLOCATED`
- `PICKING`
- `FROZEN`
- `DEFECTIVE`
- `QC_HOLD`
- `COUNT_HOLD`

## 2.3 快照层：`inventory_snapshot`

这是库位粒度快照层，由 `inventory_bucket` 重新聚合得出。

聚合维度是：

- `location_id`
- `sku_id`
- `batch_number`
- `lpn`
- `expiry_date`
- `asn_number`

数量字段包括：

- `qty_available`
- `qty_allocated`
- `qty_picking`
- `qty_frozen`
- `qty_defective`
- `qty_qc_hold`
- `qty_count_hold`
- `total_on_hand`

它的作用更偏查询优化和快照视图，不是主业务写入入口。

## 2.4 汇总层：`sku_inventory_summary`

这是按仓库+客户+SKU 做的总览层。

聚合维度：

- `warehouse_id`
- `client_id`
- `sku_id`

核心字段：

- `qty_available`
- `qty_allocated`
- `qty_picking`
- `qty_frozen`
- `qty_defective`
- `total_on_hand`
- `location_count`
- `earliest_expiry_date`

这个层更适合报表、总览页、库存总览。

## 3. 页面查询口径

## 3.1 `GET /api/v1/inventory`

默认情况下，这个接口不是直接把 `inventory_bucket` 原样返回。

它会先查所有匹配的 bucket，然后按以下维度汇总：

- `warehouseId`
- `locationId`
- `skuId`
- `batchNumber`
- `lpn`
- `expiryDate`

然后输出：

- `quantityAvailable`
- `quantityAllocated`
- `quantityPicking`
- `quantityFrozen`
- `quantityDefective`
- `quantityQcHold`
- `quantityCountHold`

所以页面看到的库存列表，本质上是“bucket 汇总视图”。

## 3.2 只有传 `bucketType` 才看原始 bucket

如果查询参数带了 `bucketType`，接口就直接返回原始 `inventory_bucket` 记录，不做二次汇总。

这个点非常重要，因为：

- 业务页面默认看的是聚合结果
- 开发排查时往往需要看原始 bucket

## 3.3 `GET /api/v1/inventory/summary`

这个接口再往上做一层聚合，按：

- `warehouseId`
- `skuId`
- `clientId`

汇总出：

- `available`
- `allocated`
- `picking`
- `frozen`
- `defective`
- `qcHold`
- `countHold`
- `total`

这是面向库存总览而不是明细排查的。

## 3.4 `GET /api/v1/inventory/transactions`

这个接口查的是 `inventory_event`，也就是库存事件流水。

它回答的是：

- 库存什么时候变了
- 因为什么变了
- 哪个单据引起的

但它不替代当前库存事实值。

## 4. 每层谁更新谁

当前真实更新关系如下：

1. 业务动作触发 service
2. service 创建 `inventory_event`
3. service 更新 `inventory_bucket`
4. `inventory_bucket` 变化后触发 `inventory_snapshot` 和 `sku_inventory_summary` 刷新
5. 查询接口读取：
   - 原始 bucket
   - 或 bucket 汇总
   - 或事件流水

## 5. 为什么 bucket 才是当前库存事实层

因为当前写路径里：

- 入库上架改 bucket
- 冻结/解冻改 bucket
- 调整改 bucket
- 移库改 bucket
- 分配/取消分配改 bucket
- 发货扣减改 bucket

而页面库存、汇总库存、快照库存，最终都从 bucket 推出来。

## 6. 边界和现实

## 6.1 `inventory_event` 记录了变化，但不保证页面直接看它

事件层是流水，不是当前库存总账。

## 6.2 `inventory_snapshot` 和 `sku_inventory_summary` 不是主事务内强一致层

它们是事务后异步刷新，失败时再尝试同步兜底。

因此：

- bucket 一定是主事实层
- snapshot/summary 是派生层

## 6.3 bucket 维度里带 `asn_number`

这表示同一货位同一 SKU，即使其他维度相同，只要来源 ASN 不同，也可能拆成不同 bucket。

## 7. 本文件小结

如果只记一件事，可以记这一句：

当前代码里的库存管理核心是 `inventory_bucket`，其他层都是围绕它展开的：

- `inventory_event` 记录变化
- `inventory_bucket` 保存当前事实
- `inventory_snapshot` 和 `sku_inventory_summary` 做派生汇总
- `inventory` 系列接口根据不同场景展示不同层的数据
