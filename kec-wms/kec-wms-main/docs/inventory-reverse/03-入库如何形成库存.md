# 入库如何形成库存

## 1. 覆盖范围

本文件只讲“入库角度的库存形成”，也就是：

- 收货为什么不直接产生库存
- 上架单生成为什么还不是库存
- 上架执行时库存到底怎么落账

重点来源：

- `backend/src/app/api/v1/asn/[id]/receiving/sku/route.ts`
- `backend/src/app/api/v1/putaway/orders/route.ts`
- `backend/src/app/api/v1/shelving/route.ts`
- `backend/src/lib/services/inventory-operation-service.ts`
- `backend/src/lib/services/inventory-event-service.ts`
- `backend/src/lib/services/inventory-bucket-service.ts`

## 2. 当前入库链里，什么时候才真正形成库存

当前代码里的答案很明确：

- 收货时不形成库存
- 创建上架单时不形成库存
- 真正形成库存是在 `POST /api/v1/shelving`

## 3. 收货为什么不直接形成库存

`POST /api/v1/asn/[id]/receiving/sku` 主要写的是：

- `asn`
- `asn_line`
- `receiving_record`
- `container`
- `container_item`
- `serial_number`

它不会写：

- `inventory_event`
- `inventory_bucket`

因此收货只是把“货已经到仓、已登记”这件事记录下来，并没有把货放进可管理库存桶。

## 4. 创建上架单为什么不形成库存

`POST /api/v1/putaway/orders` 主要写的是：

- `putaway_order`
- `putaway_order_line`
- `receiving_record.isPutawayAllocated`
- `container_item.putawayOrderLineId`
- `asn_line.status`
- `asn.status`

它本质是把“待上架工作”组织出来，不是把货落到库位。

所以这一步依然不会写：

- `inventory_event`
- `inventory_bucket`

## 5. 真正形成库存：`POST /api/v1/shelving`

## 5.1 入口分支

当前上架执行有两种：

- `mode = sku`
- `mode = container`

但两条线最终都会调用：

- `putaway(params, tx)`

## 5.2 上架前校验

当前代码会校验：

- 目标货位存在且可上架
- 目标货位未锁定
- 库区质量类型与货品质量一致
- 同货位同 SKU 不允许混不同批次
- 同货位同 SKU 不允许混不同效期
- 上架单行存在且仍有剩余数量
- 序列号数量与上架数量一致
- 序列号状态必须是 `IN_STOCK`

## 5.3 第一步：写 `inventory_event`

`putaway()` 先创建一条上架事件。

关键语义：

- 事件类型：`PUTAWAY`
- 数量增量：正数
- 关联单据：
  - `SKU_SHELVING`
  - 或 `CONTAINER_SHELVING`

这一步回答的是：

- 这次上架动作发生了
- 从业务单据角度，库存应该增加多少

## 5.4 第二步：写 `inventory_bucket`

随后通过 `updateBucketsInTransaction()` 更新 bucket。

如果是良品：

- 写入 `AVAILABLE`

如果是残品：

- 写入 `DEFECTIVE`

同时带上关键维度：

- `locationId`
- `skuId`
- `batchNumber`
- `lpn`
- `expiryDate`
- `asnNumber`
- `fifoDate`

这一步完成后，当前库存事实层才真正改变。

## 5.5 第三步：写 `putaway_detail`

每次上架都会新增 `putaway_detail`，作为动作明细。

这张表不是库存事实层，但它把一次具体上架动作完整落了下来：

- 上架到哪个货位
- 上了多少
- 对应哪个 bucket
- 对应哪个上架单行
- 用的什么设备

## 5.6 第四步：回写业务单据

上架后会继续回写：

- `putaway_order_line`
- `putaway_order`
- `asn_line`
- `asn`
- `serial_number`
- `container_item`
- `container`

这些回写不是库存本身，但它们决定业务流程是否推进到：

- `IN_PROGRESS`
- `COMPLETED`
- `PUTTING_AWAY`
- `COMPLETED`

## 5.7 第五步：事务后刷新派生层

事务提交后，触发：

- `inventory_snapshot`
- `sku_inventory_summary`

如果异步失败，代码还会尝试同步兜底刷新。

## 6. 入库形成库存时改了哪些字段

## 6.1 `inventory_event`

核心变化：

- 新增一条 `PUTAWAY` 事件
- `quantityDelta = +数量`
- 记录 `referenceType/referenceId/referenceNumber/referenceLineId`

## 6.2 `inventory_bucket`

核心变化：

- 命中已有 bucket 则 `quantity += 数量`
- 没有则创建新 bucket
- `version` 递增
- `updated_at` 更新

## 6.3 `inventory_snapshot`

不是主事务内改，而是事务后根据 bucket 重算：

- `qtyAvailable`
- `qtyDefective`
- `totalOnHand`

## 6.4 `sku_inventory_summary`

同样是事务后重算：

- `qtyAvailable`
- `qtyDefective`
- `totalOnHand`
- `locationCount`

## 7. 入库形成库存时的锁

上架会先拿：

- `withSkuLock`

然后在事务内锁：

- `putaway_order_line`
- `putaway_order`
- `asn`
- `asn_line`

真正改库存时，再由 `updateBucketsInTransaction()` 对 bucket 加锁。

所以“入库形成库存”不是单点写库，而是：

1. 锁 SKU
2. 锁业务单据
3. 锁 bucket
4. 更新事件和库存

## 8. 当前实现里的几个现实

## 8.1 收货和库存是分离的

货到仓不等于库存已经形成。

当前实现把“收货登记”和“库存形成”拆成两步：

- 收货
- 上架

## 8.2 残品库存走 `DEFECTIVE` bucket

这意味着当前系统不是把残品写进普通可用库存，而是走单独 bucket。

## 8.3 事件层和 bucket 层对残品的表达并不完全完全同构

当前 `putaway()` 创建事件时通过 `createPutawayEvent()` 记的是 `PUTAWAY` 事件，事件里的 bucket 口径和最终 bucket 写入口径需要分开理解。

文档里要按代码现实写，不做口径美化。

## 9. 本文件小结

当前代码里，入库真正形成库存的唯一关键节点是“上架执行”。

可以把它理解成：

- 收货：登记货到了
- 上架单：组织待上架任务
- 上架执行：真正把货落成库存
