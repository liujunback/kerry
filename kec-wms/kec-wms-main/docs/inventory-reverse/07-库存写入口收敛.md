# 库存写入口收敛

## 1. 原则

生产业务代码不应直接写 `inventory_bucket`。

库存数量变化必须通过统一库存服务入口完成，保证同一条链路同时具备：

- 分布式锁或业务锁
- `inventory_event` 事件流水
- `inventory_bucket` 当前事实更新
- `inventory_snapshot` / `sku_inventory_summary` 派生层刷新

盘点生成范围已异步化后，API 只提交 `INVENTORY_COUNT_SCOPE` 任务；实际 `COUNT_HOLD` 占用和源桶扣减由 worker 调用 `generateInventoryCountScope` 完成。

## 2. 允许的例外

以下场景可以直接写库存桶，但必须保持边界清晰：

- E2E 或开发环境造数
- 初始化导入或历史数据修复
- 明确的一次性运维脚本

这些例外不应复用到生产业务主链路。

## 3. 盘点生成范围链路

盘点范围生成的状态流转为：

`PENDING_SCOPE -> GENERATING_SCOPE -> READY`

失败时为：

`PENDING_SCOPE -> GENERATING_SCOPE -> SCOPE_FAILED`

重复提交规则：

- 同一盘点单存在 `PENDING` 或 `PROCESSING` 的 `INVENTORY_COUNT_SCOPE` 任务时，返回已有任务编号。
- 无运行任务且状态不在 `DRAFT`、`PENDING_SCOPE`、`SCOPE_FAILED` 时，拒绝重新提交。
- worker 启动时再次校验状态，状态不允许时不得继续生成范围。

## 4. 当前收敛目标

第一轮只收敛生成范围相关逻辑：

- 范围解析
- 库存桶筛选
- 脏盘点差异桶检查
- 盘点锁冲突检查
- `COUNT_HOLD` 转桶
- 批次和明细计划

初盘、复盘、差异确认、结算和释放 `COUNT_HOLD` 不和本轮拆分混在一起。

## 5. 已知直接写桶路径

当前静态审计不应再出现生产业务直接写 `inventoryBucket` 路径。

统一库存桶服务内部允许使用原生 SQL 更新 `inventory_bucket`，但不提供通用“删除零库存桶”入口。零库存桶可能被 `allocation_detail`、`pick_order_line`、`putaway_detail`、盘点明细或盘点锁引用，展示和汇总层应通过 `quantity > 0` 过滤。

新增生产业务代码不得再增加直接写桶路径。

库存初始化导入仍属于允许例外场景，但实现上也应先写 `ADJUST` 事件，再通过 `updateBucketsInTransaction` 计算差量后写入，避免手工维护 `inventory_snapshot` / `sku_inventory_summary`。
