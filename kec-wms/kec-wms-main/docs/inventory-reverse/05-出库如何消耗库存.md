# 出库如何消耗库存

## 1. 覆盖范围

本文件讲当前代码里库存从“可用”到“最终出库扣减”的真实链路。

重点来源：

- `backend/src/lib/services/inventory-allocation-service.ts`
- `backend/src/lib/services/checkout-service.ts`
- `backend/src/lib/services/inventory-operation-service.ts`
- `backend/src/app/api/v1/outbound-orders/batch-allocate/route.ts`
- `backend/src/app/api/v1/outbound-orders/batch-rollback/route.ts`
- `backend/src/app/api/v1/outbound-orders/[id]/rollback/route.ts`

## 2. 当前出库侧真正会改库存的节点

在当前代码里，真正清晰接到主业务入口的库存变化节点有三个：

1. 分配
2. 取消分配
3. 签出发货扣减

另外，`pick()` 服务虽然已经实现，但当前仓库中没有看到库存主链路由直接调用它。

所以本文件按“实际主入口”优先说明。

## 3. 分配：`AVAILABLE -> ALLOCATED`

## 3.1 入口

当前直接入口包括：

- `POST /api/v1/outbound-orders/batch-allocate`
- 出库订单创建后，也会通过 `queueInventoryAllocation()` 进入分配队列

## 3.2 分配前置条件

`allocateInventorySync()` 要求：

- 订单存在
- 订单状态允许分配
- 每个订单行都有足够可用库存

它在真正改库存前会先做一轮可用性检查：

- `checkInventoryAvailability()`

检查口径基于：

- `AVAILABLE` bucket

## 3.3 分配时的锁

先拿：

- `withAllocationLock(tenantId, orderId)`

然后进入事务。

事务内会再次读取订单和 bucket，避免只依赖事务外检查。

## 3.4 分配时怎么选 bucket

当前选桶策略来自：

- 客户/客户仓配置
- 默认值

策略包括：

- `FIFO`
- `FEFO`
- `LIFO`

真正选桶时，只找：

- `bucketType = AVAILABLE`

## 3.5 分配时改了什么

对每个分配片段，当前代码会做四件事：

1. 创建两条事件
   - `AVAILABLE` 减少
   - `ALLOCATED` 增加
2. 更新 bucket
   - `AVAILABLE -= qty`
   - `ALLOCATED += qty`
3. 新增 `allocation_detail`
4. 回写订单行和订单状态

## 3.6 `allocation_detail`

这是出库库存变化里非常关键的桥接表。

它记录：

- 分配来自哪个 bucket
- 分配给哪个订单/订单行
- 分配了多少
- 当前状态是 `ALLOCATED / PICKING / PICKED / SHIPPED / RELEASED / CANCELLED`

签出时也会继续用这张表找来源。

## 4. 取消分配：`ALLOCATED -> AVAILABLE`

## 4.1 入口

- `POST /api/v1/outbound-orders/batch-rollback`
- `POST /api/v1/outbound-orders/[id]/rollback`

## 4.2 前置条件

当前代码要求订单状态是：

- `ALLOCATED`
- 或 `OUT_OF_STOCK`

并且部分入口还要求：

- 订单未加入波次

## 4.3 取消分配时怎么做

`deallocateInventorySync()` 会：

1. 先拿 `withAllocationLock`
2. 查出所有 `ALLOCATED` bucket
3. 创建两条事件
   - `ALLOCATED` 减少
   - `AVAILABLE` 增加
4. 更新 bucket
5. 把订单行 `allocatedQty` 清零
6. 把订单状态恢复为 `PENDING`

这里是一个非常标准的库存回退动作：

- 从已分配库存退回可用库存

## 5. 签出发货扣减

## 5.1 真实扣减入口

当前仓库里，真正清晰调用 `ship()` 的主链在：

- `checkout-service.ts -> shipOrderInTransaction()`

这意味着库存最终扣减不是在“创建拣货单”时发生，而是在签出/签出事务里发生。

## 5.2 发货时用什么来源

代码会先查当前订单对应的：

- `allocation_detail`

只处理状态在以下范围内的分配记录：

- `ALLOCATED`
- `PICKING`
- `PICKED`

然后按分配记录决定扣减来源 bucket：

- 如果状态是 `PICKING / PICKED`
  - 从 `PICKING` bucket 扣
- 否则
  - 从 `ALLOCATED` bucket 扣

## 5.3 发货时的锁

签出时会先针对每条分配记录对应的 bucket 执行：

- `withBucketLock(...)`

然后再调用：

- `ship()`

因此扣减粒度非常细，是 bucket 级别串行。

## 5.4 发货时怎么改库存

`ship()` 的逻辑分两种：

### 指定来源 bucket 类型

如果传了 `sourceBucketType`：

- 只从指定 bucket 扣减

### 未指定来源 bucket 类型

按当前代码默认顺序：

1. 先扣 `PICKING`
2. 不够再扣 `ALLOCATED`

## 5.5 发货时改了什么

每次扣减会：

1. 创建 `SHIP` 事件
2. 更新源 bucket 数量
3. 回写 `allocation_detail`
   - `shippedQty`
   - `status = SHIPPED`
   - `shippedAt`

注意：

发货是库存真正离库，不会再向其他 bucket 回写增加。

## 6. 关于 `pick()` 的现实说明

`inventory-operation-service.ts` 里已经有：

- `pick()`

它的 bucket 变化是：

- `ALLOCATED -> PICKING`

但在当前仓库代码搜索结果里，没有看到库存主业务入口明确直接调用这条服务。

因此当前文档里的口径是：

- `pick()` 是已实现的库存操作能力
- 当前主路由里更明显接通的是：
  - 分配
  - 取消分配
  - 发货扣减

## 7. 出库库存变化总表

| 节点 | 事件 | bucket 变化 | 关键表 |
| --- | --- | --- | --- |
| 分配 | `ALLOCATE` | `AVAILABLE -> ALLOCATED` | `inventory_event` `inventory_bucket` `allocation_detail` |
| 取消分配 | `DEALLOCATE` | `ALLOCATED -> AVAILABLE` | `inventory_event` `inventory_bucket` |
| 拣货 | `PICK` | `ALLOCATED -> PICKING` | `inventory_event` `inventory_bucket` |
| 发货 | `SHIP` | `PICKING/ALLOCATED -> 出库减少` | `inventory_event` `inventory_bucket` `allocation_detail` |

## 8. 本文件小结

当前代码里，出库消耗库存的真正逻辑可以概括成一句话：

- 分配把可用库存锁成已分配库存
- 取消分配把它放回可用库存
- 发货再把已分配或拣货中的库存真正扣掉

而这一整条链的桥接核心，是：

- `allocation_detail`
