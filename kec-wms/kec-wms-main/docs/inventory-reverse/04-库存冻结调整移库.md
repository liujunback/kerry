# 库存冻结调整移库

## 1. 覆盖范围

本文件合并讲三类直接改库存的内部动作：

- 冻结 / 解冻
- 调整
- 移库

重点来源：

- `backend/src/app/api/v1/inventory/freezes/*`
- `backend/src/app/api/v1/inventory/adjustments/*`
- `backend/src/app/api/v1/inventory/transfers/*`
- `backend/src/lib/services/inventory-operation-service.ts`

## 2. 冻结 / 解冻

## 2.1 入口

- `POST /api/v1/inventory/freezes`
- `POST /api/v1/inventory/freezes/[id]/release`

## 2.2 当前实现特点

当前并没有独立的“冻结单主表”。

所谓“冻结列表”本质上是：

- 去查 `inventory_bucket`
- 过滤 `bucketType = FROZEN`

所以冻结在当前系统里更像“库存状态变更”，不是完整单据流。

## 2.3 冻结怎么改库存

`POST /inventory/freezes` 最终调用：

- `freeze()`

`freeze()` 做两件事：

1. 创建冻结事件
2. 更新 bucket

bucket 变化是：

- `AVAILABLE -= 数量`
- `FROZEN += 数量`

如果可用库存不够，直接失败。

## 2.4 解冻怎么改库存

`POST /inventory/freezes/[id]/release` 最终调用：

- `unfreeze()`

bucket 变化是：

- `FROZEN -= 数量`
- `AVAILABLE += 数量`

这里 `[id]` 实际上不是冻结单 ID，而是：

- `inventory_bucket.id`

并且要求该 bucket 当前必须是：

- `FROZEN`

## 2.5 冻结相关表变化

- `inventory_event`
  - 新增 `FREEZE / UNFREEZE`
- `inventory_bucket`
  - `AVAILABLE/FROZEN` 桶互转
- `inventory_snapshot`
  - 事务后重算
- `sku_inventory_summary`
  - 事务后重算

## 3. 调整单

## 3.1 入口

- `POST /api/v1/inventory/adjustments`
- `PUT /api/v1/inventory/adjustments/[id]`
- `DELETE /api/v1/inventory/adjustments/[id]`
- `POST /api/v1/inventory/adjustments/[id]/execute`
- `POST /api/v1/inventory/adjustments/[id]/submit`
- `POST /api/v1/inventory/adjustments/[id]/approve`
- `POST /api/v1/inventory/adjustments/[id]/reject`

## 3.2 当前实现特点

### 3.2.1 创建调整单时不改库存

创建时只写：

- `inventory_adjustment`
- `inventory_adjustment_line`

不会写：

- `inventory_event`
- `inventory_bucket`

### 3.2.2 提交/审批/拒绝接口已废弃

当前代码里：

- `submit`
- `approve`
- `reject`

这些接口都直接返回“流程已取消”。

也就是说，当前调整单流程的真实主链是：

- 创建
- 编辑
- 删除
- 直接执行

## 3.3 调整单类型

当前支持三种：

- `QUANTITY_ADJUST`
- `LOCATION_ADJUST`
- `QUALITY_ADJUST`

## 3.4 数量调整怎么改库存

执行时调用：

- `adjust()`

它会：

1. 先校验源 bucket 数量是否足够
2. 创建 `ADJUST` 事件
3. 直接修改指定 bucket 的 `quantityDelta`

也就是说，数量调整是对单个 bucket 直接增减。

## 3.5 库位调整怎么改库存

执行时调用：

- `transfer()`

它会：

1. 检查源 bucket 是否足够
2. 创建两条事件
   - `TRANSFER_OUT`
   - `TRANSFER_IN`
3. 更新两个 bucket

bucket 变化是：

- 源货位 bucket 减
- 目标货位同维度 bucket 加

## 3.6 质量调整怎么改库存

质量调整不是一条指令完成，而是当前代码分两步做：

1. `adjust()` 做一条出
2. `adjust()` 再做一条入

也就是：

- 从 `fromBucketType` 扣减
- 往 `toBucketType` 增加

当前执行前还会校验：

- 目标货位所在库区质量类型，是否允许容纳目标 bucket 类型

## 3.7 调整单执行时的锁

执行接口先对：

- `inventory_adjustment`

做 `FOR UPDATE`

然后具体库存变化继续靠：

- bucket 锁

所以当前保护逻辑是：

1. 一张调整单不能重复执行
2. bucket 不会被并发乱改

## 4. 移库单

## 4.1 入口

- `POST /api/v1/inventory/transfers`
- `PUT /api/v1/inventory/transfers/[id]`
- `DELETE /api/v1/inventory/transfers/[id]`
- `POST /api/v1/inventory/transfers/[id]/submit`
- `POST /api/v1/inventory/transfers/[id]/approve`
- `POST /api/v1/inventory/transfers/[id]/reject`
- `POST /api/v1/inventory/transfers/[id]/execute`

## 4.2 当前流程

当前真实流程是：

1. 创建草稿单 `DRAFT`
2. 提交 `PENDING`
3. 审批 `APPROVED`
4. 执行 `COMPLETED`

和调整单不同，移库单审批流当前还在用。

## 4.3 创建移库单时做什么

创建时会先校验：

- 源货位和目标货位不能相同
- 源货位 `AVAILABLE` bucket 数量足够

然后写：

- `inventory_transfer`
- `inventory_transfer_line`

但仍然不会直接改库存。

## 4.4 提交与审批做什么

### 提交

- 要求当前状态是 `DRAFT`
- 再次检查源 bucket 是否够
- 然后把单据推进到 `PENDING`

### 审批

- 要求当前状态是 `PENDING`
- 推到 `APPROVED`

### 拒绝

- 要求当前状态是 `PENDING`
- 推到 `REJECTED`

## 4.5 执行移库怎么改库存

执行时先对：

- `inventory_transfer`

做 `FOR UPDATE`

然后逐行调用：

- `transfer()`

每行执行后，再更新：

- `inventory_transfer_line.transferredQty`
- `inventory_transfer_line.status = COMPLETED`

全部完成后，主单更新：

- `inventory_transfer.status = COMPLETED`
- `executedByUserId`
- `executedAt`

## 4.6 移库的库存变化

每一条移库行都会：

- 从源 bucket 扣减
- 向目标 bucket 增加

并创建：

- `TRANSFER_OUT`
- `TRANSFER_IN`

两条事件。

## 5. 字段变化总表

| 动作 | 单据表 | 事件表 | bucket 变化 |
| --- | --- | --- | --- |
| 冻结 | 无独立冻结单 | `FREEZE` | `AVAILABLE -> FROZEN` |
| 解冻 | 无独立冻结单 | `UNFREEZE` | `FROZEN -> AVAILABLE` |
| 数量调整 | `inventory_adjustment*` | `ADJUST` | 单 bucket 增减 |
| 库位调整 | `inventory_adjustment*` | `TRANSFER_OUT/IN` | 源货位减，目标货位加 |
| 质量调整 | `inventory_adjustment*` | 两次 `ADJUST` | 源 bucket 减，目标 bucket 加 |
| 移库 | `inventory_transfer*` | `TRANSFER_OUT/IN` | 源货位减，目标货位加 |

## 6. 本文件小结

冻结、调整、移库这三类动作虽然入口不同，但最终都回到同一个库存核心：

- 写事件
- 改 bucket
- 刷新 snapshot/summary

区别主要在于：

- 有没有独立单据
- 单据流是否仍在使用
- bucket 是“同位置换状态”还是“跨位置迁移”
