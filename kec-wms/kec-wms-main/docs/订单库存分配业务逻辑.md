# 订单库存分配业务逻辑

## 概述

订单库存分配（Inventory Allocation）是WMS系统中的核心业务流程，负责将仓库中的可用库存（AVAILABLE）分配给出库订单（OutboundOrder），确保订单能够按计划拣货和发货。该模块采用事件溯源（Event Sourcing）架构，支持多种分配策略和并发控制机制。

## 核心概念

### 库存桶（Inventory Bucket）

库存桶是按多维度聚合的库存状态视图，每个桶代表特定条件下的库存数量：

- **维度**：租户 + 仓库 + 库区 + 库位 + SKU + 批次号 + LPN + 桶类型
- **桶类型（BucketType）**：
  - `AVAILABLE`：可用库存（可分配）
  - `ALLOCATED`：已分配库存（已锁定给订单）
  - `PICKING`：拣货中库存
  - `FROZEN`：冻结库存
  - `DEFECTIVE`：残次品库存
  - `QC_HOLD`：质检冻结库存
  - `COUNT_HOLD`：盘点冻结库存

### 分配策略（Allocation Strategy）

系统支持三种库存分配策略，用于决定从哪些库存桶中优先分配：

1. **FIFO（First In First Out）**：先进先出
   - 按 `fifoDate` 升序排序
   - 优先分配最早入库的库存
   - 适用于大多数标准商品

2. **FEFO（First Expired First Out）**：先到期先出
   - 按 `expiryDate` 升序排序，再按 `fifoDate` 升序
   - 优先分配最早到期的库存
   - 适用于有保质期的商品（食品、药品等）

3. **LIFO（Last In First Out）**：后进先出
   - 按 `fifoDate` 降序排序
   - 优先分配最晚入库的库存
   - 适用于特殊业务场景

### 分配模式（Allocation Mode）

系统支持两种并发控制模式：

1. **FAST 模式（快速模式）**：
   - 直接获取分布式锁
   - 适用于并发量不高的场景
   - 性能最优，但可能存在锁竞争

2. **FAIR 模式（公平队列模式）**：
   - 使用 Redis 公平队列，保证先到先得
   - 适用于高并发场景
   - 避免"饥饿"问题，但性能略低

## 分配流程

### 1. 触发分配

分配可以通过两种方式触发：

#### 异步分配（推荐）

通过 BullMQ 队列异步处理，适用于批量分配场景：

```typescript
// 调用入口：queueInventoryAllocation()
await queueInventoryAllocation(order, tenantId, userId)
```

**流程**：
1. 获取客户的分配配置（策略和模式）
2. 创建 `INVENTORY_ALLOCATION` 类型的后台任务
3. Worker 异步处理任务，支持进度跟踪
4. 任务完成后记录操作日志

#### 同步分配

直接执行分配逻辑，适用于单个订单的即时分配：

```typescript
// 调用入口：allocateInventorySync()
const result = await allocateInventorySync(orderId, tenantId, userId)
```

### 2. 配置获取

分配配置的优先级：**ClientWarehouse.config > Client.config > 默认值**

```typescript
// 默认配置
{
  strategy: 'FIFO',  // 分配策略
  mode: 'FAST'       // 分配模式
}
```

### 3. 前置检查

在执行分配前，系统会进行以下检查：

1. **订单状态检查**：订单必须处于 `CREATED` 或 `PENDING` 状态
2. **库存充足性检查**：遍历所有订单行，检查每个 SKU 的可用库存是否充足
   - 计算需求数量：`requiredQty = orderedQty - allocatedQty`
   - 查询 AVAILABLE 桶的总数量
   - 如果任何 SKU 库存不足，立即返回失败，记录日志

### 4. 库存查询与分配

#### 4.1 查询可用库存

根据分配策略查询 AVAILABLE 类型的库存桶：

```typescript
// 查询条件
WHERE:
  - tenantId = 订单租户
  - warehouseId = 订单仓库
  - skuId = 订单行SKU
  - clientId = 订单客户（可选）
  - bucketType = 'AVAILABLE'
  - quantity >= 1

// 排序规则
FIFO:  ORDER BY fifoDate ASC
FEFO:  ORDER BY expiryDate ASC, fifoDate ASC
LIFO:  ORDER BY fifoDate DESC
```

#### 4.2 分配计算

遍历每个订单行，按策略顺序从库存桶中分配：

```typescript
for (const line of order.lines) {
  const requiredQty = line.orderedQty - line.allocatedQty
  if (requiredQty <= 0) continue

  // 获取按策略排序的可用库存桶
  const buckets = await getAvailableBuckets(...)

  let remainingQty = requiredQty
  for (const bucket of buckets) {
    if (remainingQty <= 0) break

    // 计算本次分配数量（不超过桶的可用量）
    const allocateQty = Math.min(remainingQty, bucket.quantity)

    // 记录分配信息
    allocationRecords.push({
      bucketId: bucket.id,
      locationId: bucket.locationId,
      skuId: bucket.skuId,
      lineId: line.id,
      quantity: allocateQty,
      // ... 其他字段
    })

    remainingQty -= allocateQty
  }

  // 如果仍有剩余需求，说明库存不足
  if (remainingQty > 0) {
    return { success: false, message: '库存不足' }
  }
}
```

### 5. 并发控制

#### FAST 模式（快速模式）

使用分布式锁（Redis）确保并发安全：

```typescript
// 锁的粒度：仓库 + SKU
lockKey = `inventory-allocation-lock:${warehouseId}:${skuId}`

// 锁参数
LOCK_TTL_SECONDS = 60        // 锁过期时间 60 秒
LOCK_RETRY_DELAY_MS = 100    // 重试间隔 100ms
LOCK_MAX_RETRIES = 50        // 最大重试次数（总等待约 5 秒）
```

**流程**：
1. 收集订单涉及的所有 SKU，按字母顺序排序（避免死锁）
2. 依次获取每个 SKU 的分布式锁
3. 如果任何锁获取失败，释放已获取的锁，返回失败
4. 执行分配逻辑
5. 释放所有锁

#### FAIR 模式（公平队列模式）

使用 Redis 有序集合实现公平队列：

```typescript
// 队列键：仓库 + SKU
queueKey = `${warehouseId}:${skuId}`

// 队列参数
FAIR_QUEUE_WAIT_MS = 100          // 等待间隔 100ms
FAIR_QUEUE_MAX_WAIT_MS = 30000    // 最大等待时间 30 秒
```

**流程**：
1. 为每个 SKU 加入公平队列（使用订单ID作为成员）
2. 轮询检查是否所有 SKU 都排在队列第一位
3. 如果轮到自己，获取锁并执行分配
4. 分配完成后，离开所有队列

### 6. 事务执行

所有数据库操作在一个事务中完成，确保数据一致性：

#### 6.1 创建分配事件

使用事件溯源模式记录库存变化：

```typescript
// 每次分配创建 2 个事件
Event 1: AVAILABLE 桶减少（ALLOCATE_OUT）
Event 2: ALLOCATED 桶增加（ALLOCATE_IN）
```

#### 6.2 更新库存桶

```typescript
// 1. 减少 AVAILABLE 桶数量
UPDATE inventory_bucket
SET quantity = quantity - allocateQty
WHERE bucketType = 'AVAILABLE'

// 2. 增加或创建 ALLOCATED 桶
// 如果存在同维度的 ALLOCATED 桶，则增加数量
// 否则创建新的 ALLOCATED 桶
```

#### 6.3 创建分配明细

```typescript
// 创建 AllocationDetail 记录
INSERT INTO allocation_detail (
  tenantId,
  bucketId,
  locationId,
  skuId,
  batchNumber,
  lpn,
  allocatedQty,
  referenceType,      // 'OUTBOUND_ORDER'
  referenceId,        // 订单ID
  referenceNumber,    // 订单号
  referenceLineId,    // 订单行ID
  allocationType,     // 'SOFT'（软分配）
  status              // 'ALLOCATED'
)
```

#### 6.4 更新订单行

```typescript
UPDATE outbound_order_line
SET
  allocatedQty = allocatedQty + lineAllocatedQty,
  status = 'ALLOCATED'
WHERE id = lineId
```

#### 6.5 更新订单主表

```typescript
UPDATE outbound_order
SET
  totalAllocatedQty = totalAllocatedQty + totalAllocated,
  status = 'ALLOCATED'
WHERE id = orderId
```

#### 6.6 更新订单时间线

```typescript
// 记录分配时间和操作人
UPSERT INTO order_timeline (
  orderId,
  allocatedAt,
  allocatedBy
)
```

#### 6.7 更新库存快照

```typescript
// 更新 InventorySnapshot（库位级别汇总）
UPDATE inventory_snapshot
SET
  qtyAvailable = qtyAvailable - allocatedQty,
  qtyAllocated = qtyAllocated + allocatedQty
WHERE locationId = ... AND skuId = ...

// 更新 SkuInventorySummary（SKU级别汇总）
UPDATE sku_inventory_summary
SET
  qtyAvailable = qtyAvailable - allocatedQty,
  qtyAllocated = qtyAllocated + allocatedQty,
  lastMovementAt = NOW()
WHERE warehouseId = ... AND skuId = ...
```

## 取消分配（Deallocate）

当订单需要回滚或取消时，执行取消分配操作：

### 前置条件

- 订单状态必须为 `ALLOCATED`

### 执行流程

1. **查找已分配库存**：查询该订单的所有 ALLOCATED 桶
2. **创建取消分配事件**：记录 ALLOCATED -> AVAILABLE 的库存变化
3. **更新库存桶**：
   - 减少 ALLOCATED 桶数量
   - 增加 AVAILABLE 桶数量
4. **更新订单行**：将 `allocatedQty` 重置为 0，状态改为 `PENDING`
5. **更新订单主表**：将 `totalAllocatedQty` 重置为 0，状态改为 `PENDING`
6. **记录操作日志**：记录 DEALLOCATE 操作

## 并发安全机制

### 分布式锁

使用 Redis 实现分布式锁，防止同一 SKU 被并发分配：

```typescript
// 锁键格式
lockKey = `inventory-allocation-lock:${warehouseId}:${skuId}`

// 锁的生命周期
1. acquireLock(lockKey, ttl)  // 获取锁
2. 执行分配逻辑
3. releaseLock(lockKey, value) // 释放锁（finally 块中）
```

### 死锁避免

通过对 SKU ID 进行排序，确保所有线程以相同顺序获取锁：

```typescript
const skuIds = [...new Set(order.lines.map(l => l.skuId))].sort()
```

### 乐观锁

在更新库存桶时，使用 version 字段进行乐观锁检查：

```typescript
// 检查库存是否被其他任务修改
const currentBucket = await tx.inventoryBucket.findUnique({
  where: { id: bucketId },
  select: { quantity: true, version: true }
})

if (!currentBucket || currentBucket.quantity < allocateQty) {
  throw new Error('库存已被其他任务分配，请重试')
}

// 更新时递增版本号
await tx.inventoryBucket.update({
  where: { id: bucketId },
  data: {
    quantity: { decrement: allocateQty },
    version: { increment: 1 }
  }
})
```

## 异常处理

### 库存不足

- **检测时机**：预检查阶段和实际分配阶段
- **处理方式**：
  - 返回失败结果，包含缺少的数量
  - 记录 ALLOCATE_FAIL 操作日志
  - 不支持部分分配（全部成功或全部失败）

### 锁获取超时

- **FAST 模式**：重试 50 次（约 5 秒），超时后返回失败
- **FAIR 模式**：等待 30 秒，超时后返回失败

### 并发冲突

- **乐观锁冲突**：事务回滚，抛出异常，提示重试
- **分布式锁冲突**：等待重试或返回超时

## 数据流转

```
订单创建（CREATED）
    ↓
触发分配
    ↓
获取分配配置（策略 + 模式）
    ↓
预检查库存充足性
    ↓
获取分布式锁（FAST）或加入公平队列（FAIR）
    ↓
查询 AVAILABLE 桶（按策略排序）
    ↓
计算分配数量（逐桶分配）
    ↓
事务执行：
  - 创建分配事件（Event Sourcing）
  - 更新库存桶（AVAILABLE → ALLOCATED）
  - 创建分配明细（AllocationDetail）
  - 更新订单行（allocatedQty + status）
  - 更新订单主表（totalAllocatedQty + status）
  - 更新订单时间线（allocatedAt + allocatedBy）
  - 更新库存快照（InventorySnapshot + SkuInventorySummary）
    ↓
释放锁 / 离开队列
    ↓
记录操作日志
    ↓
订单状态变更为 ALLOCATED
```

## 性能优化

### 1. 索引优化

关键查询字段建立索引：
- `inventory_bucket`: `[tenantId, warehouseId, skuId, bucketType, quantity]`
- `allocation_detail`: `[referenceType, referenceId]`

### 2. 锁粒度

- 锁的粒度为 **仓库 + SKU**，而非整个仓库
- 不同 SKU 的分配可以并发执行

### 3. 批量处理

Worker 支持批量处理多个订单，减少任务创建开销：

```typescript
{
  orderIds: ['order1', 'order2', 'order3'],  // 批量订单
  warehouseId: 'warehouse1',
  allocationStrategy: 'FIFO'
}
```

### 4. 异步快照更新

库存快照（InventorySnapshot、SkuInventorySummary）的更新采用异步触发：
- 使用 `setImmediate()` 延迟到当前调用栈结束后
- 通过 BullMQ 队列异步处理
- 失败时自动降级为同步更新

## 业务规则

### 1. 全量分配原则

- 订单必须**全部分配成功**才能进入 ALLOCATED 状态
- 不支持部分分配（如果任何 SKU 库存不足，整个订单分配失败）
- 这确保了订单的完整性，避免部分履约

### 2. 软分配机制

- 分配类型为 `SOFT`（软分配）
- 库存已锁定给订单，但尚未物理移动
- 在拣货阶段才会转换为 PICKING 状态

### 3. 批次和效期管理

- 分配时保留批次号（batchNumber）和效期（expiryDate）
- ALLOCATED 桶继承源 AVAILABLE 桶的批次信息
- 支持按批次追溯和效期管理

### 4. 客户隔离

- 支持按客户（clientId）筛选库存
- 确保客户专属库存不会分配给其他客户

## 状态转换

```
订单状态流转：
CREATED/PENDING → ALLOCATED → PICKING → PICKED → PACKED → SHIPPED

库存桶状态流转：
AVAILABLE → ALLOCATED → PICKING → (出库后删除或转为其他状态)
```

## 监控指标

### 关键指标

1. **分配成功率**：`allocatedOrders / totalOrders`
2. **分配耗时**：从触发到完成的时间
3. **锁等待时间**：获取分布式锁的等待时间
4. **库存不足次数**：分配失败的次数

### 日志记录

- 所有分配操作记录到 `operation_log` 表
- 包含操作类型、状态变化、操作人、时间戳
- 支持审计和问题追溯

## 常见问题

### Q1: 为什么不支持部分分配？

**A**: 全量分配原则确保订单完整性。如果支持部分分配，会导致：
- 订单拆分复杂度增加
- 拣货和打包流程混乱
- 客户体验下降（收到不完整的订单）

### Q2: FAST 和 FAIR 模式如何选择？

**A**:
- **FAST 模式**：适用于并发量不高的场景（< 10 并发），性能最优
- **FAIR 模式**：适用于高并发场景（> 10 并发），避免某些订单长时间等待

### Q3: 为什么使用事件溯源？

**A**: 事件溯源提供：
- 完整的库存变化历史
- 可追溯性和审计能力
- 支持时间旅行查询（查询任意时间点的库存状态）
- 便于问题排查和数据修复

### Q4: 如何处理分配后订单取消？

**A**: 调用 `deallocateInventorySync()` 取消分配：
- 将 ALLOCATED 桶的库存归还到 AVAILABLE 桶
- 订单状态回退到 PENDING
- 库存重新可用，可分配给其他订单

## 技术架构

### 服务层

- **inventory-allocation-service.ts**：核心分配逻辑（同步执行）
- **inventory-allocation.worker.ts**：队列 Worker（异步执行）
- **inventory-bucket-service.ts**：库存桶管理
- **inventory-event-service.ts**：事件溯源管理
- **inventory-lock-service.ts**：分布式锁管理

### 队列系统

- **队列名称**：`INVENTORY_ALLOCATION`
- **处理器**：InventoryAllocationWorker
- **并发数**：可配置（默认 5）
- **重试策略**：失败后自动重试 3 次

### 缓存和锁

- **Redis**：分布式锁、公平队列
- **锁键格式**：`inventory-allocation-lock:${warehouseId}:${skuId}`
- **队列键格式**：`fair-queue:${warehouseId}:${skuId}`
