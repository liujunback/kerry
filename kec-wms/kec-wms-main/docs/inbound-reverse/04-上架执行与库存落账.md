# 上架执行与库存落账

## 1. 覆盖范围

本文件覆盖下面这些当前后端入口：

- `GET /api/v1/shelving/location`
- `POST /api/v1/shelving`
- `GET /api/v1/inventory`

重点解释这些表：

- `putaway_detail`
- `inventory_event`
- `inventory_bucket`
- `inventory_snapshot`
- `sku_inventory_summary`
- `putaway_order`
- `putaway_order_line`
- `asn`
- `asn_line`
- `serial_number`
- `container`
- `container_item`

## 2. 货位校验：`GET /api/v1/shelving/location`

## 2.1 作用

给上架作业端校验目标货位是否合法。

## 2.2 当前校验规则

货位必须满足：

- 存在
- 属于当前租户
- 如果传了 `warehouseId`，还必须属于指定仓库
- `status = 'ACTIVE'`
- `isReceivable = true`
- `lockStatus != 'LOCKED'`

会把这些关键属性返回给前端：

- `locationCode`
- `zoneId`
- `zoneName`
- `zoneCode`
- `zoneQualityType`
- `locationType`
- `warehouseId`

读接口本身不写库。

## 3. 上架执行：`POST /api/v1/shelving`

## 3.1 两种模式

当前上架执行分两条：

- `mode = 'sku'`
  - 基于上架单行执行
- `mode = 'container'`
  - 基于容器货品执行

两条链最后都会调用：

- `inventory-operation-service.putaway`

也就是说，库存落账的核心是共用的。

## 4. SKU 上架模式

## 4.1 前置校验

### 4.1.1 SKU 与序列号

如果 SKU 启用了序列号管理：

- `serialNumbers.length` 必须等于 `quantity`
- 每个序列号都必须已存在于 `serial_number`
- 且状态必须是 `IN_STOCK`

### 4.1.2 目标货位

货位必须：

- 存在
- 未锁定
- `isReceivable = true`

### 4.1.3 上架单行定位

定位逻辑分两层：

1. 如果传了 `putawayLineId`
   - 支持逗号分隔多个 ID
   - 查出所有匹配上架单行
2. 否则
   - 按 `skuId`
   - 再按 `putawayOrderId` 或 `warehouseId`
   - 找一条状态在 `PENDING / IN_PROGRESS` 的行

### 4.1.4 同库位混放约束

当前代码会先查目标货位是否已有该 SKU 的库存桶。

如果已有，则要求：

- 效期必须一致
- 批次必须一致

否则直接拒绝上架。

这意味着当前实现不允许把同 SKU 的不同批次、不同效期压到同一个货位上。

### 4.1.5 库区质量区校验

当前代码会比较：

- 货位所属库区 `zone.qualityType`
- 上架单行的 `qualityType`

约束如下：

- 良品只能上到良品库区
- 残品不能上到良品库区

## 4.2 锁与数量分摊

### 4.2.1 锁

SKU 上架先用：

- `withSkuLock(tenantId, warehouseId, skuId)`

再在事务内对本次涉及的 `putaway_order_line` 做 `FOR UPDATE`。

### 4.2.2 支持跨多行消耗

如果前端传的是合并后的多个 `putawayLineId`，当前代码会：

- 把这些行按 `remainingQty` 降序排序
- 优先消耗剩余量最大的行
- 把本次上架数量逐步分配到多条底层上架单行

因此：

- 前端看到的一条合并任务
- 可能对应底层多条 `putaway_order_line` 被同时更新

## 4.3 实际库存落账：先写事件，再写库存桶

上架执行最终调用 `putaway(params, tx)`。

这个服务做两件核心事情：

### 4.3.1 写 `inventory_event`

通过 `createPutawayEvent` 新增一条库存事件。

关键字段：

- `tenantId`
- `clientId`
- `warehouseId`
- `locationId`
- `skuId`
- `skuCode`
- `batchNumber`
- `lpn`
- `eventType = 'PUTAWAY'`
- `bucketType`
  - 服务里创建事件时写的是 `AVAILABLE`
- `quantityDelta = +上架数量`
- `referenceType`
  - SKU 模式是 `SKU_SHELVING`
  - 容器模式是 `CONTAINER_SHELVING`
- `referenceId`
- `referenceNumber`
- `referenceLineId`
- `operatorId`
- `quantityBefore`
- `quantityAfter`

### 4.3.2 写 `inventory_bucket`

随后通过 `updateBucketsInTransaction` 更新库存桶。

当前库存桶唯一维度非常关键：

- `locationId`
- `skuId`
- `batchNumber`
- `lpn`
- `expiryDate`
- `bucketType`
- `asnNumber`

这意味着当前库存不是简单按“库位 + SKU”聚合，而是细分到：

- 批次
- 效期
- 库存桶类型
- ASN 来源号

上架时写入的关键字段：

- `tenantId`
- `clientId`
- `warehouseId`
- `zoneId`
- `locationId`
- `skuId`
- `skuCode`
- `batchNumber`
- `lpn`
- `asnNumber`
- `bucketType`
  - 良品时 `AVAILABLE`
  - 残品时 `DEFECTIVE`
- `quantity += 本次数量`
- `fifoDate`
  - 优先用 `asn.signedAt`
  - 否则 `asn.actualArrivalAt`
  - 再否则当前时间
- `expiryDate`

## 4.4 上架后回写的业务表

### 4.4.1 `putaway_detail`

每次实际上架都会新增一条 `putaway_detail`，作为动作明细。

关键字段：

- `detailNumber`
- `putawayOrderId`
- `putawayLineId`
- `skuId`
- `skuCode`
- `skuName`
- `batchNumber`
- `lotNumber`
- `expiryDate`
- `qualityType`
- `quantity`
- `locationId`
- `locationCode`
- `bucketId`
- `containerId`
- `containerCode`
- `serialNumbers`
- `putawayAt`
- `putawayBy`
- `deviceType`

### 4.4.2 `putaway_order_line`

SKU 模式下可能更新多条；容器模式下一般更新一条。

共同回写字段：

- `putawayQty += 本次分配数量`
- `remainingQty -= 本次分配数量`
- `status`
  - 还有剩余则 `IN_PROGRESS`
  - 没剩余则 `COMPLETED`
- `startedAt`
  - 首次实际上架才写
- `completedAt`
  - 该行完成时写
- `updatedBy`

### 4.4.3 `putaway_order`

回写：

- `putawayQty += 本次上架数量`
- `pendingQty -= 本次上架数量`
- `status`
  - 全部完成时 `COMPLETED`
  - 否则 `PARTIAL`
- `putawayStartTime`
  - 首次实际上架才写
- `putawayEndTime`
  - 整单完成时写
- `updatedBy`

### 4.4.4 `asn_line`

每个被分摊到的上架单行，如果挂了 `asnLineId`，都会同步回写：

- `putawayQty += 本次分摊数量`
- `status`
  - 若 `putawayQty >= receivedQty`，写 `COMPLETED`
  - 否则写 `PUTAWAY`
- `updatedBy`

### 4.4.5 `asn`

回写：

- `totalPutawayQty += 本次上架数量`
- `putawayStartAt`
  - 首次实际上架才写
- `status`
  - 如果收货未完结且当前仍在 `RECEIVING`，状态可以保持不变，只累计上架量
  - 如果收货已完结，且当前是 `RECEIVED` 但未全部上架，写 `PUTTING_AWAY`
  - 如果收货已完结且全部上架完成，写 `COMPLETED`
- `putawayEndAt`
  - ASN 全部上架完成时写
- `completedAt`
  - ASN 全部上架完成时写
- `updatedBy`

## 4.5 序列号回写

如果 SKU 是序列号管理，并且本次传了序列号，会更新 `serial_number`：

- `warehouseId`
- `putawayAt = now`
- `putawayOrderId`
- `updatedBy`

注意：

- 收货阶段是“创建序列号”
- 上架阶段是“补齐上架归属和上架时间”

## 5. 容器上架模式

## 5.1 与 SKU 模式的共同点

以下逻辑和 SKU 模式一致：

- 校验目标货位
- 校验质量区
- 调用 `putaway()`
- 写 `inventory_event`
- 写 `inventory_bucket`
- 写 `putaway_detail`
- 更新 `putaway_order_line`
- 更新 `putaway_order`
- 更新 `asn_line`
- 更新 `asn`
- 更新 `serial_number`

## 5.2 容器模式的差异点

### 5.2.1 来源不是上架单行组合，而是 `container_item`

当前代码先找：

- `containerId`
- `skuId`
- `batchNumber`
- `qualityType`
- `quantity >= 本次上架量`

找不到就失败。

### 5.2.2 容器货品扣减

上架成功后，会把 `container_item.quantity` 减少：

- 若剩余数量大于 `0`
  - 更新该行数量
- 若剩余数量小于等于 `0`
  - 直接删除该 `container_item`

### 5.2.3 容器清空复位

如果该容器已经没有任何 `container_item`，则自动把 `container` 复位为：

- `workStatus = 'IDLE'`
- `currentAsnId = null`
- `currentBatchNumber = null`
- `currentQualityStatus = null`
- `currentSkuId = null`
- `closedAt = null`

这个动作很关键，因为它决定该容器后续是否还能重新投入入库使用。

## 6. 事务后异步刷新：快照和汇总

## 6.1 `inventory_snapshot`

上架事务结束后，会触发 `triggerSnapshotUpdate`。

这不是主事务内写入，而是事务后异步更新。

`updateLocationSnapshot` 的口径是：

- 从 `inventory_bucket` 重新聚合
- 按以下维度生成快照：
  - `locationId`
  - `skuId`
  - `batchNumber`
  - `lpn`
  - `expiryDate`
  - `asnNumber`

快照里的核心数量字段：

- `qtyAvailable`
- `qtyAllocated`
- `qtyPicking`
- `qtyFrozen`
- `qtyDefective`
- `qtyQcHold`
- `qtyCountHold`
- `totalOnHand`

## 6.2 `sku_inventory_summary`

同样在事务后异步刷新。

聚合维度是：

- `warehouseId`
- `clientId`
- `skuId`

核心字段：

- `qtyAvailable`
- `qtyAllocated`
- `qtyPicking`
- `qtyFrozen`
- `qtyDefective`
- `totalOnHand`
- `locationCount`
- `earliestExpiryDate`

## 6.3 异步失败时的补偿

当前实现里，如果异步触发失败，会立即尝试同步调用：

- `updateLocationSnapshot`
- `updateSkuSummary`

所以快照和汇总不是“只靠队列，失败就算了”，而是有同步兜底。

## 7. 库存查询口径：`GET /api/v1/inventory`

## 7.1 这个接口默认查的不是原始库存桶

当前 `GET /api/v1/inventory` 默认行为是：

- 先查 `inventory_bucket`
- 再按以下维度做汇总：
  - `warehouseId`
  - `locationId`
  - `skuId`
  - `batchNumber`
  - `lpn`
  - `expiryDate`

然后返回给前端这些汇总字段：

- `quantityAvailable`
- `quantityAllocated`
- `quantityPicking`
- `quantityFrozen`
- `quantityDefective`
- `quantityQcHold`
- `quantityCountHold`

所以前端看到的“库存明细”其实是基于库存桶汇总后的视图，不是 `inventory_event`。

## 7.2 指定 `bucketType` 时才会直接看原始库存桶

如果查询参数里带了 `bucketType`，接口会：

- 直接返回原始 `inventory_bucket` 记录
- 不再做汇总

这在排查“为什么页面库存和事件流水不一致”时非常重要。

## 8. 字段回写矩阵

| 表 | 字段 | 写入时机 | 值来源 | 事务 |
| --- | --- | --- | --- | --- |
| `inventory_event` | `event_type/quantity_delta` | 上架落账 | `putaway()` | 是 |
| `inventory_bucket` | `quantity/bucket_type/asn_number` | 上架落账 | `updateBucketsInTransaction()` | 是 |
| `putaway_detail` | `*` | 每次上架 | 当前上架动作 | 是 |
| `putaway_order_line` | `putaway_qty/remaining_qty/status` | 上架 | 本次分摊 | 是 |
| `putaway_order` | `putaway_qty/pending_qty/status` | 上架 | 汇总本次结果 | 是 |
| `asn_line` | `putaway_qty/status` | 上架 | 本次分摊 | 是 |
| `asn` | `total_putaway_qty/status` | 上架 | 汇总本次结果 | 是 |
| `serial_number` | `putaway_at/putaway_order_id` | 带序列号上架 | 当前上架动作 | 是 |
| `container_item` | `quantity` 或删除 | 容器上架 | 扣减本次数量 | 是 |
| `container` | `work_status/current_*` | 容器清空后 | 容器复位 | 是 |
| `inventory_snapshot` | `qty* / total_on_hand` | 事务后 | 由库存桶重算 | 否，异步 |
| `sku_inventory_summary` | `qty* / total_on_hand` | 事务后 | 由库存桶重算 | 否，异步 |

## 9. 当前代码里必须如实写明的几个现实

### 9.1 事件层和展示层不是一层数据

当前实现是明显分层的：

- `inventory_event`
  - 流水
- `inventory_bucket`
  - 当前库存事实
- `inventory_snapshot`
  - 库位粒度快照
- `sku_inventory_summary`
  - SKU 汇总
- `GET /api/v1/inventory`
  - 对库存桶的查询视图

因此不能把“事件流水有一条 PUTAWAY”直接等同于“页面上立刻出现一行库存明细”，中间还经过库存桶和快照/汇总口径。

### 9.2 上架允许在 `RECEIVING` 状态下发生

当前代码里，ASN 上架状态校验允许：

- `RECEIVING`
- `RECEIVED`
- `PUTTING_AWAY`

也就是说，边收边上架在实现层面是被允许的。

但是：

- 只有在 `receivingEndAt` 已经存在时
- ASN 才可能最终被标记为 `COMPLETED`

### 9.3 `putaway()` 创建事件时的桶类型与实际库存桶类型存在实现差异

当前 `inventory-operation-service.putaway()` 在创建事件时调用的是 `createPutawayEvent`，这个函数默认把事件 `bucketType` 写成 `AVAILABLE`。

但实际更新库存桶时，会根据质量类型决定写：

- 良品：`AVAILABLE`
- 残品：`DEFECTIVE`

因此“残品上架”的事件层表达和库存桶层表达并不完全同构，文档必须按当前实现如实写出来，不能擅自替代码统一口径。

## 10. 本阶段小结

上架执行阶段才是当前入库模块真正“落库存”的地方。

它的真实顺序是：

1. 校验目标货位、批次、效期、质量区、数量、序列号
2. 写 `inventory_event`
3. 写 `inventory_bucket`
4. 写 `putaway_detail`
5. 回写上架单、ASN、序列号、容器
6. 事务后刷新 `inventory_snapshot` 和 `sku_inventory_summary`

如果要排查“为什么库存不对”，应该优先沿这条链逐层看，而不是只看页面或只看某一张表。
