# 收货执行与收货完结

## 1. 覆盖范围

本文件覆盖下面这些当前后端入口：

- `GET /api/v1/asn/[id]/receiving/lookup-sku`
- `POST /api/v1/asn/[id]/receiving/sku`
- `POST /api/v1/asn/[id]/receiving/complete`

重点解释这些表：

- `asn`
- `asn_line`
- `receiving_record`
- `container`
- `container_item`
- `serial_number`

## 2. 收货前的查询入口：`GET /api/v1/asn/[id]/receiving/lookup-sku`

## 2.1 作用

根据条码在指定 ASN 中定位可收货的明细行，并把当前 SKU 的收货上下文返回给前端。

## 2.2 前置条件

- 用户必须登录
- ASN 必须存在
- ASN 必须已签收，也就是 `signedAt` 不能为空

## 2.3 匹配规则

当前代码按下面条件查 ASN 行：

- `asnLine.skuCode == barcode`
- 或 `asnLine.sku.barcode == barcode`

查询结果里会返回：

- 命中的 `asnLine`
- 对应 `sku`
- `availableBatchLines`
  - 只保留 `receivedQty < expectedQty` 的可继续收货行

## 2.4 读接口本身不改数据

这个接口只做校验和定位，不写库。

## 3. 收货提交：`POST /api/v1/asn/[id]/receiving/sku`

## 3.1 作用

这是当前真正执行收货的核心接口。名字虽然是 `receiving/sku`，但实际既支持：

- `SKU` 收货
- `CONTAINER` 收货

区别主要由入参 `receivingMode` 决定。

## 3.2 当前真实前置条件

### 3.2.1 ASN 级别

- ASN 必须存在
- ASN 必须已签收
- ASN 状态必须属于：
  - `CREATED`
  - `PENDING_RECEIVING`
  - `RECEIVING`

虽然代码允许 `CREATED`，但正常主链里签收后会进入 `PENDING_RECEIVING`，所以正常收货通常从 `PENDING_RECEIVING` 开始。

### 3.2.2 ASN 行级别

- `asnLineId` 必须存在，且属于当前 ASN
- 本次 `receivedQty` 不能大于该行剩余可收数量
  - 公式：`expectedQty - receivedQty`

### 3.2.3 SKU 管理策略

如果 SKU 开启了对应管理能力，则会触发额外校验：

- 批次管理：
  - `batchNumber` 不能为空
- 效期管理：
  - `expiryDate` 不能为空
  - `expiryDate` 不能早于今天
- 序列号管理：
  - `serialNumbers` 不能为空
  - 序列号数量必须等于本次收货数量

### 3.2.4 收货模式切换限制

当前代码会读取 `asn.receiving_method`。

逻辑要点：

- 如果 `receiving_method` 还没定，则本次收货会把该值写成当前 `receivingMode`
- 如果之前已经用某种模式开始收货，则后续不能切换到另一种模式
- 特殊点：
  - 代码把值为 `NORMAL` 的情况当成 `null` 处理

## 3.3 收货时的锁

当前接口在事务里显式加锁，避免并发重复收货：

- 先锁 `asn`
- 再锁 `asn_line`
- 如果是容器收货，还会锁 `container`

因此这条链是带悲观锁的，不是纯乐观更新。

## 3.4 SKU 收货与容器收货的共同写库

不管是 `SKU` 模式还是 `CONTAINER` 模式，下面这几步都是共同的。

### 3.4.1 更新 `asn_line`

每次收货都会回写：

- `receivedQty += 本次收货数量`
- `receivedGoodQty += 本次良品数量`
- `receivedDamagedQty += 本次残品数量`
- `batchNumber`
  - 优先用本次传入
- `expiryDate`
  - 优先用本次传入
- `serialNumbers`
  - 如果本次有序列号，会追加到原有 JSON 数组
- `status`
  - 若累计收货已到 `expectedQty`，写 `RECEIVED`
  - 若累计收货大于 `0` 但未收满，写 `RECEIVING`

### 3.4.2 更新 `asn`

每次收货都会回写：

- `totalReceivedQty += 本次收货数量`
- `totalReceivedLines = 已收货行数`
- `receivingStartAt`
  - 首次收货才写
- `receiving_method`
  - 首次收货才写
- `status`
  - 首次收货：从 `CREATED / PENDING_RECEIVING` 推到 `RECEIVING`
  - 非容器模式下，如果所有行都已收满，直接写 `RECEIVED`
- `receivingEndAt`
  - 仅在非容器模式且所有行收满时直接写入

### 3.4.3 写 `receiving_record`

每次提交都会新增一条 `receiving_record`，字段包括：

- `recordNumber`
  - 当前代码临时生成
- `asnId`
- `asnLineId`
- `containerId`
  - 容器模式时才有
- `warehouseId`
- `clientId`
- `skuId`
- `skuCode`
- `skuName`
- `expectedQty`
- `receivedQty`
- `goodQty`
- `damagedQty`
- `batchNumber`
- `expiryDate`
- `serialNumbers`
- `receivingMode`
- `deviceType`
  - 当前代码这里直接写 `PC`
- `status = 'COMPLETED'`
- `receivedAt`
- `receivedBy`
- `notes`
  - 如果带容器，会记“容器编码”

### 3.4.4 写 `serial_number`

如果本次带序列号，当前代码会：

1. 先检查本次提交里是否重复
2. 再检查库里是否已存在同仓库、同状态 `IN_STOCK` 的相同序列号
3. 校验通过后批量写入 `serial_number`

收货时新建的关键字段：

- `tenantId`
- `clientId`
- `skuId`
- `serialNumber`
- `status = 'IN_STOCK'`
- `warehouseId`
- `receivedAt`
- `receivedAsnId`
- `createdBy`

注意：

- 收货阶段不会写 `putawayOrderId`
- 收货阶段不会写 `putawayAt`

这些要到上架阶段再写。

## 3.5 只有容器收货才会触发的写库

## 3.5.1 容器前置约束

如果 `receivingMode = 'CONTAINER'`，当前代码要求：

- `containerId` 或 `containerCode` 至少提供一个
- 若只传 `containerCode`，会先反查容器

容器必须满足：

- `enabledStatus = 'ENABLED'`
- `workStatus != 'CLOSED'`

如果容器处于 `OCCUPIED` 且 `currentAsnId` 不是当前 ASN：

- 先检查 `container_item` 是否还有内容
- 若还有内容，则拒绝本次收货
- 若没有内容，则自动把容器重置成空闲

## 3.5.2 容器内一致性约束

当前代码要求，同一个容器内已存在货品时，本次继续收货必须与容器内现有货品保持一致：

- `batchNumber` 必须一致
- `expiryDate` 必须一致
- `qualityType` 必须一致

也就是说，同一容器不允许混：

- 不同批次
- 不同效期
- 不同质量状态

## 3.5.3 更新 `container`

容器参与收货后，会回写：

- `workStatus = 'OCCUPIED'`
- `lastOccupiedTime = now`
- `currentAsnId = 当前 ASN`
- `updatedBy = 当前用户`

当前代码在收货阶段不会显式写：

- `currentBatchNumber`
- `currentQualityStatus`
- `currentSkuId`

这些字段虽然存在于模型里，但这条主写链没有真正维护完整。

## 3.5.4 更新或新增 `container_item`

当前代码会按如下维度找是否已有未挂上架单的容器明细：

- `containerId`
- `asnId`
- `skuId`
- `batchNumber`
- `qualityType`
- `putawayOrderLineId = null`

命中则更新：

- `quantity += 本次数量`
- `serialNumbers` 追加

没命中则新增一条 `container_item`，写入：

- `tenantId`
- `containerId`
- `asnId`
- `asnLineId`
- `skuId`
- `skuCode`
- `skuName`
- `quantity`
- `batchNumber`
- `expiryDate`
- `qualityType`
- `serialNumbers`
- `receivedAt`
- `receivedBy`

## 3.6 收货状态与日志

收货提交事务结束后，代码会按状态变化记录 ASN 状态日志：

- 从 `CREATED / PENDING_RECEIVING` 到 `RECEIVING`
  - 记录 `START_RECEIVE`
- 到 `RECEIVED`
  - 记录 `COMPLETE_RECEIVE`

## 3.7 字段回写矩阵

| 表 | 字段 | 写入时机 | 值来源 | 事务 |
| --- | --- | --- | --- | --- |
| `asn_line` | `received_qty` | 每次收货 | 累加本次数量 | 是 |
| `asn_line` | `received_good_qty` | 良品收货 | 累加本次数量 | 是 |
| `asn_line` | `received_damaged_qty` | 残品收货 | 累加本次数量 | 是 |
| `asn_line` | `batch_number` | 收货 | 本次值优先 | 是 |
| `asn_line` | `expiry_date` | 收货 | 本次值优先 | 是 |
| `asn_line` | `serial_numbers` | 收货 | 追加 JSON 数组 | 是 |
| `asn_line` | `status` | 收货 | `RECEIVING/RECEIVED` | 是 |
| `asn` | `total_received_qty` | 每次收货 | 累加本次数量 | 是 |
| `asn` | `total_received_lines` | 每次收货 | 当前已收货行数 | 是 |
| `asn` | `receiving_start_at` | 首次收货 | 当前时间 | 是 |
| `asn` | `receiving_end_at` | 非容器模式收满 | 当前时间 | 是 |
| `asn` | `receiving_method` | 首次收货 | 当前模式 | 是 |
| `asn` | `status` | 收货 | `RECEIVING/RECEIVED` | 是 |
| `receiving_record` | `*` | 每次收货 | 当前提交上下文 | 是 |

| `container` | `work_status/current_asn_id` | 容器收货 | 当前容器上下文 | 是 |
| `container_item` | `quantity` 等 | 容器收货 | 更新或新增 | 是 |

## 4. 收货完结：`POST /api/v1/asn/[id]/receiving/complete`

## 4.1 作用

这是一个“收尾接口”，用于把正在收货中的 ASN 从 `RECEIVING` 结束到 `RECEIVED`。

## 4.2 当前真实前置条件

- 用户必须登录
- ASN 必须存在
- 当前状态必须是 `RECEIVING`

## 4.3 实际写库

事务里会做两件事：

### 4.3.1 批量更新 `asn_line`

把当前 ASN 下状态在以下范围内的行全部改成 `RECEIVED`：

- `PENDING`
- `RECEIVING`

注意：

- 这里没有按“是否真的收满”逐行判断
- 它是一个偏业务收尾动作，不是重新校验明细收满逻辑

### 4.3.2 更新 `asn`

直接写：

- `status = 'RECEIVED'`
- `receivingEndAt = now`
- `notes`
  - 若请求传了 `notes`，则覆盖/沿用

## 4.4 操作日志

接口结束后会通过 `operationLogService.logOperation` 记录一条 ASN 操作日志，带上：

- `beforeStatus`
- `afterStatus = 'RECEIVED'`
- `shortageCount`

其中 `shortageCount` 来自：

- `receivedQty < expectedQty` 的明细行数量

## 4.5 当前代码里需要如实说明的地方

### 4.5.1 `completeReceivingSchema` 已定义，但这条主链没有真正接入

`backend/src/lib/validations/receiving.ts` 里定义了：

- `createDiscrepancy`
- `handlingMethod`
- `putawayMethod`
- `createPutawayTasks`

但当前 `POST /api/v1/asn/[id]/receiving/complete` 没有用这个 Schema 做完整校验，也没有按这些选项去真正驱动差异处理或自动上架任务生成。

### 4.5.2 `ReceivingDiscrepancy` 在当前主链里不是自动生成主角

虽然模型和校验都存在，但当前实际收货主链里：

- `POST /api/v1/asn/[id]/receiving/sku`
- `POST /api/v1/asn/[id]/receiving/complete`

都没有自动创建 `receiving_discrepancy`。

所以文档只能如实写成：

- “表和能力已存在”
- “当前这条主链未自动落地”

而不能写成“系统会自动生成收货差异单”。

## 5. 本阶段小结

当前代码里的收货阶段，本质上做了三层事情：

1. 把 ASN/ASN 行的收货数量和状态推起来
2. 把每次收货动作落成 `receiving_record`
3. 如果是容器收货，再把容器当前占用状态和容器内明细一起维护起来

这个阶段依然没有真正形成库存。真正把货落到库存层，是后面的上架执行阶段。
