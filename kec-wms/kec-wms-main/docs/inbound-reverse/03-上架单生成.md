# 上架单生成

## 1. 覆盖范围

本文件覆盖下面两个当前后端入口：

- `POST /api/v1/putaway/orders`
- `GET /api/v1/shelving/putaway-order`

重点解释这些表：

- `putaway_order`
- `putaway_order_line`
- `receiving_record`
- `container_item`
- `asn`
- `asn_line`
- `serial_number`

## 2. 创建上架单：`POST /api/v1/putaway/orders`

## 2.1 作用

把“已收货但尚未进入上架执行”的数据组织成上架任务。

当前接口支持两条来源：

- 任务模式：基于 `receiving_record`
- 容器模式：基于 `container_item`

## 2.2 入参

当前校验来自路由内部 `createOrderSchema`：

- `putawayMode`
  - `CONTAINER_MODE`
  - `TASK_MODE`
- `asnLineIds`
  - 任务模式常用
- `containerIds`
  - 容器模式常用
- `separateByQuality`
  - 当前默认 `true`

注意：

- 当前实现里 `separateByQuality` 有入参定义，但主逻辑并没有复杂展开成单独策略模块，它更多体现在按良品/残品拆行处理。

## 2.3 共通前置条件

- 用户必须登录
- 至少要选中一类待上架来源：
  - `asnLineIds`
  - 或 `containerIds`

如果两者都空，直接失败。

## 3. 任务模式：基于 `receiving_record`

## 3.1 选数规则

当前代码会从 `receiving_record` 里找满足条件的记录：

- `tenantId = 当前租户`
- `asnLineId in asnLineIds`
- `isPutawayAllocated = false`
- `status = 'COMPLETED'`

也就是说，只有“已经完成收货、还没被分配到上架单”的收货记录才会进入本次上架单生成。

## 3.2 分组规则

当前实现按 `asnId` 分组。

结果是：

- 同一次请求里，如果选中了多个 ASN 行
- 只要它们属于不同 ASN
- 就会按 ASN 拆成多张上架单

## 3.3 生成 `putaway_order`

每个 ASN 分组会新建一张 `putaway_order`，写入：

- `tenantId`
- `putawayOrderNumber`
- `warehouseId`
- `clientId`
- `asnId`
- `asnType`
- `putawayMode`
- `status = 'PENDING'`
- `totalQty`
- `pendingQty = totalQty`
- `putawayQty = 0`
- `skuCount`
- `lineCount`
- `containerCount = 0`
- `createdBy`

## 3.4 生成 `putaway_order_line`

当前代码不是按 `receiving_record` 原样一条一条搬，而是先把每条收货记录拆成“良品数量一行”和“残品数量一行”两种候选。

对于每条 `receiving_record`：

- `goodQty > 0` 时，生成一条 `qualityType = GOOD`
- `damagedQty > 0` 时，生成一条 `qualityType = DAMAGED`

每条 `putaway_order_line` 会写：

- `tenantId`
- `putawayOrderId`
- `lineNumber`
- `asnId`
- `asnLineId`
- `receivingRecordId`
- `skuId`
- `skuCode`
- `skuName`
- `quantity`
- `remainingQty = quantity`
- `putawayQty = 0`
- `batchNumber`
- `expiryDate`
- `qualityType`
- `status = 'PENDING'`
- `priority = 'MEDIUM'`
- `createdBy`

## 3.5 对来源数据的回写

生成任务模式上架单后，还会同步回写来源数据：

### 3.5.1 更新 `receiving_record`

- `isPutawayAllocated = true`

### 3.5.2 更新 `serial_number`

如果收货记录带序列号，会把状态为 `IN_STOCK` 的对应序列号更新成：

- `putawayOrderId = 当前上架单 ID`

注意：

- 这里只是挂上架单归属
- 还没有写 `putawayAt`

### 3.5.3 更新 `asn_line`

对本次涉及到的 `asnLineId`，统一写：

- `status = 'PUTAWAY'`

这里的含义更接近“已经进入上架阶段”，不是“已经上架完成”。

### 3.5.4 更新 `asn`

如果满足：

- `asn.receivingEndAt` 已有值
- 且 `asn.status == 'RECEIVED'`

则把 ASN 推进到：

- `status = 'PUTTING_AWAY'`

并在事务外记录状态变更日志：

- 动作：`START_PUTAWAY`

## 3.6 并发保护

当前代码会在事务内使用 `FOR UPDATE` 锁住本次涉及的 `receiving_record`。

目的很明确：

- 防止同一批收货记录被重复创建上架单
- 防止并发情况下 `isPutawayAllocated` 检查失效

## 4. 容器模式：基于 `container_item`

## 4.1 前置条件

当前代码要求所选容器必须：

- 存在
- 属于当前租户
- `workStatus = 'CLOSED'`

也就是说，容器模式创建上架单之前，容器必须先关箱。

## 4.2 选数规则

从 `container_item` 查满足条件的明细：

- `containerId in containerIds`
- `tenantId = 当前租户`
- `putawayOrderLineId = null`

只有尚未挂到上架单行的容器货品，才会被纳入。

## 4.3 分组规则

和任务模式一致，仍然按 `asnId` 分组，一组一张上架单。

## 4.4 生成 `putaway_order`

写入逻辑与任务模式类似，差异主要是：

- `putawayMode = 'CONTAINER_MODE'`
- `containerCount` 按容器数量统计

## 4.5 生成 `putaway_order_line`

每个 `container_item` 直接生成一条上架单行，写入：

- `tenantId`
- `putawayOrderId`
- `lineNumber`
- `asnId`
- `asnLineId`
- `skuId`
- `skuCode`
- `skuName`
- `quantity`
- `remainingQty = quantity`
- `putawayQty = 0`
- `batchNumber`
- `expiryDate`
- `containerId`
- `qualityType`
- `status = 'PENDING'`
- `priority = 'MEDIUM'`
- `createdBy`

## 4.6 对来源数据的回写

### 4.6.1 更新 `container_item`

生成上架单行后，会回写：

- `putawayOrderLineId = 对应上架单行 ID`

### 4.6.2 更新 `serial_number`

若 `container_item` 带序列号，会把对应序列号写成：

- `putawayOrderId = 当前上架单 ID`

### 4.6.3 更新 `asn`

若收货已完结且当前状态是 `RECEIVED`，同样把 ASN 推进到：

- `PUTTING_AWAY`

并记录状态机日志 `START_PUTAWAY`。

## 5. 查询上架单：`GET /api/v1/shelving/putaway-order`

## 5.1 作用

根据 `putawayOrderNumber` 查询上架单详情，供上架作业端使用。

## 5.2 默认会做任务合并

当前接口默认把多条上架单行按如下维度合并成展示任务：

- `skuCode`
- `batchNumber`
- `expiryDate`
- `qualityType`
- `containerId`

如果不想合并，需要显式传：

- `merge=false`

## 5.3 为什么这个点很重要

因为上架执行接口 `POST /api/v1/shelving` 支持前端传入逗号分隔的多个 `putawayLineId`。

这正对应了“查询时合并展示，但执行时仍要回写多条底层上架单行”的实现方式。

## 5.4 返回内容

接口会返回：

- `putawayOrder` 基础信息
- `warehouse`
- `client`
- `asn`
- `putawayTasks`
- `progress`

其中 `progress` 主要基于：

- `totalQty`
- `putawayQty`
- `pendingQty`
- `taskCount`
- `completedTaskCount`

## 6. 字段回写矩阵

| 表 | 字段 | 写入时机 | 值来源 | 事务 |
| --- | --- | --- | --- | --- |
| `putaway_order` | `status` | 创建上架单 | 固定写 `PENDING` | 是 |
| `putaway_order` | `total_qty/pending_qty` | 创建上架单 | 收货记录或容器明细汇总 | 是 |
| `putaway_order_line` | `quantity/remaining_qty` | 创建上架单行 | 来源数量 | 是 |
| `putaway_order_line` | `quality_type` | 创建上架单行 | 良品/残品或容器明细质量 | 是 |
| `receiving_record` | `is_putaway_allocated` | 任务模式 | 固定写 `true` | 是 |
| `container_item` | `putaway_order_line_id` | 容器模式 | 对应上架单行 ID | 是 |
| `asn_line` | `status` | 任务模式 | 固定写 `PUTAWAY` | 是 |
| `asn` | `status` | 收货完成后创建上架单 | `RECEIVED -> PUTTING_AWAY` | 是 |
| `serial_number` | `putaway_order_id` | 有序列号时 | 当前上架单 ID | 是 |

## 7. 当前代码里的几个现实约束

### 7.1 上架单不是库存

创建上架单阶段只是把“待上架工作”组织出来，并不会：

- 写 `inventory_event`
- 写 `inventory_bucket`
- 写 `putaway_detail`

库存真正增加，要等后面的上架执行。

### 7.2 `asn_line.status = PUTAWAY` 不代表已上架完成

在当前实现里，这个状态更接近：

- “已被分配到上架流程”

真正上架完成还要看：

- `asn_line.putawayQty`
- `putaway_order_line.status`
- `putaway_order.status`
- `asn.totalPutawayQty`

### 7.3 查询接口默认合并展示，和底表行数不是一回事

因此做排查时必须区分：

- 展示层任务
- 底层 `putaway_order_line`

## 8. 本阶段小结

当前上架单生成阶段的本质是：

1. 从收货结果或容器结果中挑出“尚未分配”的数据
2. 把这些数据组织成可执行上架任务
3. 把 ASN 和明细推进到“已进入上架流程”的状态

这一步依然没有直接改库存，只是为真正的上架落账做准备。
