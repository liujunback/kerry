# 清点处理方式与照片

## 1. 清点查找

`POST /api/v1/returns/counting/lookup` 按物流单号查找可清点退件单，允许状态：

- `SIGNED`
- `COUNTING`
- `WAIT_DISPOSITION`

如果退件单不存在或状态不允许，会返回业务错误。

## 2. 保存清点明细

`POST /api/v1/returns/[id]/count-lines` 会调用 `saveReturnCountLine`：

1. 校验退件单属于当前仓库，且状态为 `SIGNED` 或 `COUNTING`。
2. 按条码查找 SKU（商品），并校验属于该客户。
3. 如果 SKU（商品）启用批次管理，必须录入 `batchNumber`。
4. 如果 SKU（商品）启用效期管理，必须录入 `expiryDate`。
5. 校验容器存在、启用，且用途必须是 `RETURN_INBOUND`（退件入库）。
6. 校验退件暂存库位存在、启用、未锁定、可收货，且库位类型是 `STAGING`（暂存）。
7. 优先复用原预报明细；如果找不到可复用明细，则新增拆分明细。
8. 更新容器为占用状态，并写当前质量状态。
9. 主单进入 `COUNTING`。

当前清点不会直接增加库存，只记录退件清点事实和暂存信息。

## 3. 完成清点

`POST /api/v1/returns/[id]/complete-counting` 会检查：

- 至少有一条 `countedQty > 0` 的清点明细。
- 每条已清点明细必须绑定容器。
- 每条已清点明细必须绑定退件暂存库位。
- `DAMAGED`（破损）明细必须上传照片。

通过后，所有已清点明细进入 `WAIT_DISPOSITION`（等待处理方式），主单写入 `countCompleteTime` 并刷新汇总。

## 4. 照片上传

`POST /api/v1/returns/photos` 负责上传照片：

- 仅支持 `jpg`、`png`、`webp`
- 单张最大 5MB
- 上传后返回 URL（统一资源定位符）

照片本身由清点明细的 `photoUrls` 字段引用。

## 5. 客户处理方式

`POST /api/v1/returns/[id]/dispositions` 保存处理方式：

- `GOOD_PUTAWAY`：良品上架
- `DAMAGED_PUTAWAY`：破损品上架
- `DESTROY`：销毁

校验规则：

- 只能处理 `WAIT_DISPOSITION` 或 `DISPOSITION_RECEIVED` 状态的已清点明细。
- `GOOD_PUTAWAY` 只能用于 `GOOD` 明细。
- `DAMAGED_PUTAWAY` 只能用于 `DAMAGED` 明细。
- 处理方式累计数量不能超过明细已清点数量。
- `DESTROY` 会直接让对应处理方式进入 `COMPLETED`，不会生成退件上架候选。

## 6. 外部处理方式入口

`POST /api/v1/returns/by-number/[preReturnNo]/dispositions` 是按预报退件号写入客户处理方式的外部入口，需要 `return:disposition`（退件处理方式）scope（权限范围）。

该入口支持按 `returnLineNo`（退件明细号）或 `skuCode`（商品编码）定位退件明细。
