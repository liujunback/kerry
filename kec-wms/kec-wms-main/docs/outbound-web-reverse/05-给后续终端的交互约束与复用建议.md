# 给后续终端的交互约束与复用建议

## 1. 目标

本文不是在描述其他终端现状，而是从当前 Web 端出库 UI 中提炼出：

- 后续终端最值得继承的交互规则
- 哪些边界和节奏建议直接保留
- 哪些 Web 特有结构不必照搬

## 2. 必须继承的交互原则

## 2.1 单页只服务一个当前工作对象

当前 Web 非常强调：

- 当前订单
- 当前拣货单
- 当前板号/袋号
- 当前集运单

任何时刻都应有一个明确的“当前对象”。

## 2.2 扫描优先，手输补位

当前 Web 主路径始终是扫码。

手输只在这些场景出现：

- 数量输入
- 特定编码补录
- 包材选择的兜底输入

## 2.3 成功后自动推进

当前 Web 几乎每个核心执行页都有这个特征：

- 成功后清空当前输入
- 自动聚焦到下一个输入点
- 回到下一轮扫描准备态

## 2.4 错误后不清空整页上下文

当前 Web 大多数错误不会把整个页面状态清空，只会：

- toast 报错
- 清空当前错误输入
- 焦点打回当前关键输入点

## 2.5 前端先挡一层边界

当前 Web 不只是依赖后端报错，还在前端先做一层快速约束：

- 未锁定主对象前，不允许继续扫下一步
- 条件不满足时按钮禁用
- 待关箱时不允许继续扫 SKU

## 3. Web 里值得直接复用的状态模型

## 3.1 打包页

建议直接复用这套抽象：

- 当前工作对象
- 当前模式
- 当前待关箱对象
- 当前包材列表
- 当前焦点目标
- 当前序列号采集状态

## 3.2 签出页

建议直接复用这套抽象：

- 当前仓库
- 当前签出类型
- 当前容器
- 当前渠道
- 当前记录列表
- 当前统计值

## 3.3 集运页

建议直接复用这套抽象：

- 当前集运单
- 当前渠道
- 当前挂载记录
- 当前统计值

## 4. 需要明确继承的边界规则

建议直接继承这些 Web 端边界：

- 没有当前主单据时，不允许进入后续扫描
- 没有当前容器时，不允许扫订单或运单
- 没有当前集运单时，不允许扫签出单
- 待关箱状态下，不允许继续扫 SKU
- 必要前置条件不满足时，主按钮禁用

## 5. Web 里不一定要照搬的部分

后续终端不一定要原样复用这些东西：

- 大表格
- 多条件筛选器
- 批量勾选
- 行内更多菜单
- 管理页式双栏密集信息

这些更像 Web 管理台能力，不是执行终端必须保留的形式。

## 6. 更适合后续终端怎么继承

更推荐把 Web 端逻辑翻译成这种结构：

- 顶部：
  - 当前工作对象摘要
- 中部：
  - 当前唯一主输入框
- 底部：
  - 当前主动作按钮
- 次级区域：
  - 最近记录
  - 当前进度
  - 必要的错误提示

## 7. 最值得保留的五条规则

如果只保留五条，我建议保留这五条：

1. 任何时刻都要有明确的当前工作对象。
2. 主路径必须是扫码，手输只是补位。
3. 成功后自动回到下一轮扫描准备态。
4. 出错后只回退当前输入，不清空整页上下文。
5. 所有关键边界都要在前端先挡一层。

## 8. 小结

当前 Web 端出库 UI 最有价值的，不是视觉，而是“作业节奏”：

- 先锁定上下文
- 再连续推进
- 每次只完成一个明确动作
- 做完立刻进入下一轮

这套节奏非常适合后续终端继续沿用。
